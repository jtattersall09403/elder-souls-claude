## 2. Determinism — the claim is true and the claim is weak, and both matter

"Four rests return bit-identical state" is a weaker sentence than it sounds. I ran **36
populations** — 6 start hours (17:00, 03:00, 23:30, 00:00, 11:999, 20:58) × {4, 8, 12} rests ×
{with a kill between each rest, without} × **40 repeats each** — and every population returned
**exactly one distinct trace**, where the trace is the full fingerprint (`timeOfDay`,
`awardTimeOfDay`, `dayCount`, `_clockFrames`, `_awardFrames`, `phase`, `daylight`, `weather`,
`weatherRegion`, `frontProgress`, `sightlineM`, `soulsHeld`, `frame`) after **every** rest, not just
at the end. The claim holds far past where it was made.

### Is float ordering load-bearing here, as it was in the sibling piece?

**For the clock: no, and that is a design decision this file made on purpose.** `environment.js`
carries an integer frame counter and derives hours from it. I ran the accumulate-a-float clock it
replaced over one game day: `Σ 24/259200` for 259,200 terms lands on **24.00000000009578**, not 24.
The integer counter cannot drift, and `Math.round(x*1e6)/1e6` pins the published value onto
`sim/state.js`'s q6 save grid, so the value the step publishes is a value the save can hold exactly.
The sibling piece's IEEE-754 defect cannot reach the clock.

**For the weather machine sitting in the same file: yes, and nobody has said so.** `_roll()` walks
`m.states` in array order accumulating `acc += w[i]` and returns the first id whose partial sum
exceeds the draw. I re-ran 40,000 frames with `weather.json`'s state array **reversed** and the
world settles on a different weather (`canopy_dim` → `still`). That is not a defect today — the
array order is stable because it comes from a JSON array — but it means the weather machine's
determinism is a property of a **data file's key order**, not of its arithmetic, and any future
generator that emits the states from an object or a `Map` changes the weather without changing a
line of code. Recorded in §9.

## 5. The 151× — what it is actually measuring

`0.003703 h` against `0.559259 h` is presented as a **151× gap**. It is arithmetic:

* `0.559259 h` = 6,040 f@60 = 40 deaths × 151 f@60 (`SURFACE_FRAMES = 150`, `death.js:28`, plus the
  one frame the killing blow lands on, when the player is still alive at the top of `sim/step.js`'s
  frame order).
* `0.003703 h` = 40 f@60 = one frame per death, the same residual round 3 characterised.
* **151 = 6,040 ÷ 40 = `SURFACE_FRAMES + 1`.** Given this fixture the ratio could not have taken any
  other value. It is a restatement of "the hold is total", not an independent magnitude — and it is
  a measurement of **round 3's** fix, not round 4's.

**Is the small arm small because time does not pass, or because nothing measured it?** Because time
does not pass, and the instrument *is* able to go red: the same 6,040 f@60 spent **alive** burn
`0.559259 h` in the same probe, and my own arms reproduce both (`0.003888 h` dying vs `0.559444 h`
alive — my 42 frames rather than 40 because my fixture spends two extra frames per kill, which is
mine and not the world's). The claim stands; the "151×" framing does not add anything to it and
should be retired in favour of "40 f@60 against a ceiling of 41".

## 7. Two consequences of the second clock that nobody has named

The fix buys AR-1 by letting the two clocks **diverge** while a death is in flight, at
**0.013889 h per death** (150 f@60), discharged at the next rest, `setTimeOfDay` or load. Both
consequences below are measured, not argued
(`corpus/90-verdicts/wave1/artifacts/W1-13-r4/critic-clock.json` §G).

### 7a. The souls economy and the province can disagree about whether it is night

From 20:42, **22 deaths** put the award clock at **21.008** while the world clock is still at
**20.702**. The same ordinary enemy pays **57** — the night price — while **38 of 115 interiors are
open** and the province is going about its evening. This is **not** an AR-1 failure: living those
same frames pays 57 as well, which is the whole point of the fix. But it is a state the world can be
put into by dying, it is reachable in a single boss attempt, and no instrument in the round reports
it.

### 7b. A save and a reload buy back the night rate — 42 souls become 57

`save/state.js:344–348` persists `clock.time_of_day`, `clock.day_count` and `clock.weather`.
**`_awardFrames` and `awardTimeOfDay` are in neither the blob nor the loader.** A load therefore
writes `env.timeOfDay` from outside the step, `_syncFromFloat` re-seats the award clock on it, and
the offset vanishes. Near the **dawn** edge the offset runs *against* the player, so discharging it
is a gain:

| | world clock | award clock | one `inf_trash` pays |
|---|---:|---:|---:|
| from 04:48, 20 deaths, no rest | 4.802 | 5.078 | **42** |
| the same state, saved and reloaded | 4.802 | 4.802 | **57** |

Same enemy, same save, no world event in between, **+35% for a reload**. This is the
loss-compensation *family* `RI-JRN06` D9 and AR-1 exist to police, arrived at from a direction
neither of them names, and it is invisible to `m_d4_across_death_diff` and `m_d10_d11_preserved` by
construction — they diff the **save blob**, and the field is not in it. **Remedy:** put
`clock.award_frames` in the blob and read it back, so a round trip is neutral. One field, one line
each side, and `m_d4` starts covering it for free.

## 15. Secondary observations

* **`weather.json`'s state array order is load-bearing** and nothing says so. `_roll()` accumulates
  `acc += w[i]` in array order and returns the first id whose partial sum exceeds the draw;
  reversing the array changes the settled weather after 40,000 f@60 from `canopy_dim` to `still`.
  The clock beside it is immune by construction (integer counter — the accumulate-a-float clock it
  replaced drifts 9.6e-11 h per game day). Not a defect; a latent coupling to a serialiser.

  now carry `status: "measured" | "unmeasurable"` at the top level and the pass/fail lives *inside*

  passing rows. Round 3's `path_to_ten` item 7 asked for the top-level `ok` to be **split**; it has
  instead been made less legible. `journey.ok` is still `!anyUnmeasurable`.
