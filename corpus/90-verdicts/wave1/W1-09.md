## 3. The thin-weapon tunnelling test — the builder's flagged risk, run

This was the assignment's headline question, so here is the whole chain of evidence.

**Step 1 — the premise is confirmed.** `RI-CMB04` §C derives `SUBSTEPS = 4` from an assumed worst
case of 0.433 m/frame giving "≈ one capsule radius" per substep. Measured per-substep travel in
capsule radii, at 4 substeps:

```
dagger 1.33   axe 1.06   greatsword 1.33   ultra-greatsword 1.68
straight-sword 2.19   spear 2.59   halberd 2.90
```

The halberd samples at **2.90 radii per substep**, not 1. The rationale is invalid.

**Step 2 — under the model that rationale assumes, a 0.06 m pole tunnels.** Marching a
0.06 m-radius vertical pole over a 0.005 m × 0.05 m grid (32,841 positions per class) against the
recorded socket track, comparing the continuous swept hull against **discrete sampling at 5 poses**:

| class | continuous hits | positions the 4-substep discrete model misses |
|---|---|---|
| halberd | 18,965 | **282** |
| straight sword | 11,822 | **98** |
| ultra greatsword | 18,782 | 93 |
| spear | 6,548 | 36 |
| greatsword | 18,572 | 34 |
| dagger | 2,234 | 8 |
| axe | 2,809 | 8 |

So the builder was right to flag it: **had the sweep been implemented as §C's pseudocode reads
(sample 5 poses per frame), a 0.06 m pole would be missed at up to 1.5 % of the positions it
occupies.**

**Step 3 — the shipped build does not implement that model, and therefore does not tunnel.**
Three independent measurements say so:

- **Forcing `substeps` 4 → 1** in `game/data/combat/hitgeometry.json` and re-running the whole
  comparison changed **nothing**: the same 168 sim answers, the same lateral crossing at
  1.120/1.125 m, the same forward crossing at 2.225/2.230 m, zero disagreements with the analytic
  (`critic-geo2-substeps1.json` vs `critic-geo2.json`). The data file was reverted with
  `git checkout` immediately afterwards; `git status` is clean.
- The sim **hits five placements that a two-pose-only test misses** (straight sword at 1.17 and
  1.26 m; halberd at 0.81, 0.90 and 1.17 m), which proves it covers the space *between* frame
  poses. Sweeping is real, not decorative.
- The sim's boundary matches the **continuous** analytic surface to within 0.0022 m.

**Conclusion.** There is **no thin-weapon tunnelling** in this build. The sweep is a convex hull
between poses, for which the substep count changes coverage only in the concave interior of an
arc, not along it — so under-sampling by ×2.9 costs a little precision, never a missed hit.

**But this is also a check the item cannot currently distinguish.** `RI-CMB04` M2's second half
says: *"Re-run with substeps forced to 1 and confirm the sim now produces misses; if it does not,
sweeping is not actually implemented and the substep parameter is decorative."* I ran it, it
produced no misses, and the inference the item draws from that is **false here** — sweeping *is*
implemented. M2 is written for a discrete-pose implementation and mis-fires on a hull one. That is
a corpus defect, filed as `corpus_extended` with a proposed sharper discriminator (§9), and it is
why M2 scores 15 of 25 rather than 25 or 0.

## 8. Ruling on `AMENDMENT-W1-09-01`: **EARNED**

`RI-CMB09` §3 prints *"Regen recovered between chained rolls — 52 f elapsed < 42 f delay re-armed
every 52 f → delay never expires — **0**"*. 52 is not less than 42.

I reproduced the amendment's arithmetic from my own trace, pressing `roll` on every frame for 900
frames at seed 1337 (`critic-rollspam.json`):

```
roll starts:  2, 54, 106, 158, 210, 262, 314, 378, 450, 523, …
cadence:      52, 52, 52, 52, 52, 52, 64, 72, 73, …        ← the economy breaking the cadence
stamina:      21.75 at f262 (after six rolls)   6.50 at f314 (after seven)
first input dropped for insufficient stamina:   frame 366
stamina floor reached:                          0.0, never negative
```

Every printed figure in the amendment's "Measured" block reproduces: **seven** rolls before denial
(the item prints five), **frame 366** (the item prints 260), **21.75** after six rolls, which is
`120 − 6×22 + 5×6.75` exactly. Separately, my regeneration probe shows the first regenerating
frame at `f0 + 43` and the next spend at `f0 + 52`, giving **nine** regenerating frames per cycle
and `9 × 0.75 = 6.75` — the amendment's number, not zero.

It is earned on all four counts a rejected amendment fails: it corrects a **derived** table against
the item's own two binding constants rather than asking for a threshold to move; it is
demonstrable arithmetically *and* in a live trace; it changes no frame count, cost, pool or delay
anywhere; and it makes the item **harder** to satisfy, since `RP2`'s counters now need 40 % longer
to fire. One nitpick for the record, which does not change the ruling: the proposed *"Stamina at
denial — 6.5"* is the residue after the last affordable roll; the bar at the denial frame itself
reads **14.0**. Both are defensible readings of the row it replaces, and the row it replaces has
the same ambiguity.

**Recommendation to the doctrine owner: accept it as written.**

## 9. Corpus extensions filed

1. **`RI-CMB04` M2 — sharper discriminator.** M2's substeps-forced-to-1 test infers "sweeping is
   not implemented" from "no new misses". That inference holds only for a discrete-pose sweep. For
   the convex-hull sweep this build ships, reducing substeps *widens* coverage in the concave
   interior of an arc and narrows it nowhere, so the tell can never fire however broken the build
   is. Proposed replacement: measure **phantom coverage in the arc's concave interior** — place the
   target inside the chord of the swing and require sim = analytic there — and add the 0.06 m pole
   fixture M2 already names but which no build ships.
2. **`RI-CMB01` / `RI-CMB02` blind pairs — degenerate when the build is exact.** Both packs
   compared bit-identical vectors. A blind pair whose two sides coincide when the work is correct
   cannot discriminate; it needs a discriminator that varies *within* correctness (e.g. the shape
   of the roll's per-frame root-delta curve, or the commitment grid's buffered/ignored boundary).
3. **`verdict.schema.json` — the 10/10 fields.** `reference_items` has `additionalProperties:
   false` and no `why_not_ten` / `path_to_ten` / `ten_by_wave`, which `SCORING.md` §0 makes
   mandatory on pain of VOID. Carried in §5's table and in each item's `justification` string, as
   `W1-01` did. Already filed by that verdict; re-filed because it bit this one too.
4. **`HARNESS.md` §3 — two missing hooks.** `RI-CMB03` M5 says *"set stamina to
   `dmg×(1−stability) − 1` and block"*, and `RI-CMB04` M2 says *"re-run with substeps forced to
   1"*. Neither is reachable through `window.__HARNESS`. I got the first by sprinting the bar down
   for 600 frames and then `teleport`-ing back to the enemy, and the second by editing a data file
   and reverting it. Both are fixture gymnastics standing in for a one-line hook:
   `setStamina(v)` and `setSweepSubsteps(n)`.
