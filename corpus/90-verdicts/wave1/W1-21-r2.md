### 1.1 `ui-metrics.mjs` FD8 — the builder's own new check catches the builder's own declaration

FD8 is round 2's answer to the round-1 defect. It is a good check and it is written to fail in
both directions: an unmeasured screen with no declaration is a hole, and *a declaration for a
screen that did measure is a stale excuse*. The builder wrote it, added one declaration, and did
not run it. It fires on the declaration:

```
FAIL FD8 every screen opened produced a stem sample, or is declared prose-free with a reason
   — opened [book,inventory,journal,levelup,map,sheet,spells]; unmeasured [-];
     undeclared [-]; stale declarations [map]
```

The declaration in `tools/metrics/ui-metrics.mjs` `NO_PROSE.map` reads: *"S35 permits no
numerals, no labels and no legend on this screen. Its only text is a single place name under the
stick, which is a label and not body prose. There is nothing here for a stem transition to be
measured across."* The map screen draws **two** `kind: 'hint'` elements with text —
`map.hint` (76 characters of control legend) and `map.found` (a sentence) — and it produced a
stem sample in **all four** capture configurations:

```
map 1280x720@1   306 samples   map 1280x720@2  1056 samples
map 1920x1080@1  656 samples   map 1920x1080@2 2113 samples
```

The declaration is not a judgement call that went the other way. It is a factual claim about the
author's own screen that is wrong, and the check they wrote to catch exactly that kind of claim
was one command away from telling them.

### 1.2 `ui-metrics.mjs` FD6 — failing since round 1, named in no verdict

```
FAIL FD6 M-F19.1 no alpha fringing at UI edges — worst edge deviation 99.9
```

The threshold in the tool is 40. **Every one of the 28 captures exceeds it** (range 40.4 – 99.9).
This is not new: the round-1 re-run recorded in `reports/runs/UI-METRICS/ui-metrics.json` at
`2026-08-07T21:58:30Z` says `FAIL FD6 … worst edge deviation 114`, and the round-1 verdict —
which discusses this same artifact at length in its §6 — does not mention FD6 anywhere. It has
been red across two rounds and two verdicts.

Two things a next round needs to know rather than re-derive:

* **The threshold is not the item's.** `RI-UIX06` §Scoring gives FD6 as *"no fringing; **ΔE ≤3**"*
  with a hard fail at *"ΔE >8"*. The tool measures a **luminance overshoot in 0–255** and
  compares it to 40. Those are different quantities in different units, so neither the pass
  condition nor the hard-fail condition in the item is currently being tested. A 99.9 luma
  overshoot is a large number, but nobody can say from this artifact whether it is a ΔE of 3 or
  of 30 — which decides whether FD6 is a fail or a **hard fail capping the fidelity side at 2**.
* The map's four captures are the four worst on the sheet (78.8 / 75.6 / 91.8 / 91.2), so
  adding the map to `SCREENS` made an already-failing check worse rather than exposing it.

### 1.3 `ui-forbidden.mjs` — first run against any build, red, and red for the wrong reason

The round-1 verdict recorded that this tool *"has still never been run against any build"*. It
now has been, with `--self-test`, and it exits 1:

```
self-test: injected "247" -> 10 digit glyphs found
U4 declared PASS  — 0 hits []
U5 observed FAIL  — 66 digit glyphs, 0 nameplate bars, across 6 enemy regions
```

**U5's 66 hits are false positives**, and I checked rather than reported. Cropping the frame at
the bounding boxes the tool returned gives an enemy's helmet crest and jaw — lit polygon edges on
a character model, magnified 5×, in
`docs/shots/2026-08-08-w1-21-r2-critic-ui-forbidden-false-positive.png`. There is no floating
damage number in this build. Three defects in the instrument, all concrete:

1. **It scans the wrong part of the frame.** `__HARNESS.screenshot()` returns **1920×1080** —
   `index.html`'s canvas attribute — while the tool computes each enemy's screen position in the
   **1280×720** viewport space it launched with, and it never pins the drawing buffer. Every
   400×400 "region around the enemy" is therefore offset by a factor of 1.5.
   `tools/analysis/ui-layer.mjs` opens with `setDevicePixelRatio(1)` and a comment describing
   precisely this hazard; `ui-forbidden.mjs` has neither.
2. **`hit_frame: null`.** The method requires the capture to be *"at the frame after a `hit`
   event"*. No `HIT` fired in 180 frames — the swing never connected. The tool records the null
   in its artifact and grades the frame anyway.
3. **The glyph signature matches world geometry.** Its own self-test found **10** digit glyphs
   where **3** digits were drawn; the seven extra are the same background blobs the run reports.
   The calibration band (height 8–44 px, aspect 0.30–1.15, 20–400 px of ink, density 0.14–0.75)
   describes a lit crest as well as it describes a numeral.

The same six bounding boxes recur across four of the six "enemy regions" — the windows overlap —
so 66 is a multiple count of roughly sixteen distinct blobs.

**U4 declared PASS is the more interesting half, because it is unfalsifiable from its artifact.**
`out.declared` records only *hits*. There is no field anywhere in `ui-forbidden.json` saying how
many elements were scanned, or that the five menus were opened at all. A run that opened nothing
and a run that opened five screens produce a byte-identical `"declared": []`. That is question A
in its purest form and it is discussed in §2.

The round-1 defect was a check that reported PASS over a set the grader had first filtered the
unmeasurable screens out of. Round 2 fixed that check. It did not fix the shape. Here is every
detector this piece ships, with what it samples, whether the artifact records the count, and
whether the check can return PASS having measured nothing.

| Detector | Check | Samples this run | Count in artifact? | PASS on zero samples? |
|---|---|---|---|---|
| `marker-scan.mjs` | K1 | 559 files | printed, not graded | **yes** — 0 files ⇒ 0 hits ⇒ PASS |
| `ui-layer.mjs` | K2 | 9 viewpoints of 10 declared | `viewpoints_run`, `covered_all_viewpoints:false` | **yes** — `[].reduce(…)===0`, and `covered_all_viewpoints` is not in the exit code |
| `ui-layer.mjs` | instrument agreement | 9 | yes | **yes** — `[].every(…)` is `true` |
| `ui-forbidden.mjs` | U4 declared | **not recorded at all** | **no** | **yes**, and it is undetectable from the artifact |
| `ui-forbidden.mjs` | U5 observed | 6 enemy regions | `observed.length` | **yes** — two `reduce`s over `[]` are both 0 |
| `marker-diff.mjs` | K3 | 10 differentials | `K6_counts` | **yes** — `[].every(…)` |
| `marker-diff.mjs` | K4 | 3 yaw positions × 24 | `K6_counts` | **yes**, and *silently*: a missing state hits a bare `catch { continue }` |

| `ui-metrics.mjs` | FD7 | 28 panels | no | **yes** — `gradient_bits === null \|\| >= 7` passes *on absence, by construction* |
| `ui-metrics.mjs` | FD8 | 7 screens | yes | **no** — guarded in both directions. This is the fix. |
| `ui-census.mjs` | U4b, U8, U6 | — | no | **yes** |
| `ui-census.mjs` | U7, U10 | — | yes | **no** — `spend_events > 0`, `regen_blocked_frames > 0` |

Two observations the table is worth making for.

**The author already knows the rule.** `ui-census.mjs` U10 opens `o.stamina.spend_events > 0 &&
…` and U7 closes with `&& o.stamina.regen_blocked_frames > 0`. Those are exactly the guard the
round-1 verdict asked for, written by the same hand, sitting two lines from U8 — `Object.values(
o.bar_contrasts).every(…)` — which passes on an empty object. The remedy is not a new idea for
this piece; it is applying an idea it already had, uniformly.

**And the literal is still there, one line above the field that was fixed for being a literal.**
`game/src/ui/system.js` line 985, inside the `map:` compliance block:

```js
map: {
  exists: true,
  reachable_from_journal: …,
  journal_reachable_from_map: …,
  markers: 0,                    // ← a hard-coded literal
  routes_drawn: els.filter(…).length,
```

`markers` — the single field whose name is the thing S8 and S35 forbid — is not measured. It is
typed. The identical field is typed again at the top level of `getUIState()`. Round 1's §3.3
found `mutator_arities` was *"a hand-written literal of three names"*; round 2 replaced it with a
real enumeration four lines below this one and left this one alone.

A smaller instance of the same shape: `routes_drawn`, `quest_bearing_elements`,
`travel_affordances` and `numeric_text` all filter on `e.id.startsWith('map.')`. When the map is
closed there are no `map.*` elements, so every one of them evaluates to empty and the block
reports full compliance — a green AR-2 report computed over zero elements, available from any
mode.

## 3. (B) The doors — re-measured with real keys and a real pad, and they are there

This is the round's real achievement and it survives a harder instrument than the one that
produced it.

The builder's own `w1-21-r2-nav.mjs` drives `queueInputs()`, which injects **action names**
straight onto the pipeline. That is a genuine measurement of the UI state machine and it is
blind to the entire device layer: an action bound to no key, or to a key the real listener drops,
passes it. So I measured the layer underneath. `setMode('play-instrumented')` is the one mode in
which `game/src/input/real.js`'s `window` `keydown` listener is attached *and* `stepFrames()`
still drives the simulation, and every press below is a Playwright `keyboard.down` /
`keyboard.up` around a single fixed step.

**Controls first**, because "the key worked" is otherwise a claim about the harness:

```
ok  B0  real.attached=true, mode=play-instrumented, touch_controls_drawn=0
ok  B1  CONTROL: KeyQ — bound to nothing — world -> world
ok  B1b CONTROL: Escape — bound to `menu`   — world -> inventory
```

**The ring, walked with `Digit3` only, from the world:**

```
world -> inventory -> journal -> sheet -> spells -> map -> levelup -> world
```

| Screen | In, by real keys | Out, by real keys |
|---|---|---|
| `inventory` | `KeyM` | `Escape` → `world` |
| `journal` | `KeyM`, `Digit3` ×1 | `Escape` → `world` |
| `sheet` | `KeyM`, `Digit3` ×2 | `Escape` → `world` |
| `spells` | `KeyM`, `Digit3` ×3 | `Escape` → `world` |
| `map` | `KeyM`, `Digit3` ×4 | `Escape` → `world` |
| `levelup` | `KeyM`, `Digit3` ×5 | `Escape` → `world` |

**And on a pad**, through `__HARNESS.gamepad()` — `RealInput.pollGamepad()`'s own path, not a
keyboard run wearing a different label — button **9** then button **15** six times:

```
world -> inventory -> journal -> sheet -> spells -> map -> levelup -> world -> inventory
```

`Digit4` / `swap_left` from the inventory goes straight to `world`, which is the ring behaving
correctly rather than a hole: `world` is index 0 and one step left from index 1 closes the screen.

Round 1 measured **two** of six. This is six of six, in both directions, on two devices, and the
whole result reproduced identically across two independent runs of my probe. `levelup` is in the
ring only at a hearth and this run reaches the hearth through `setAtHearth(true)` rather than by
walking to one — declared, not hidden; the other five need no world state at all.

**The fight stays a fight.** `walk_live` is `false` in `world` mode and `true` with a screen open
out of combat, and `swap_left` remains half of the offhand chord in a fight. I could not
independently confirm the in-combat arm, and I say so rather than implying coverage: `aggro()`
threw before I could enter combat — see §7.1.

## 7. What the round did not touch, and what I could not do

### 7.1 `aggro()` takes the process down, and I reproduced it independently

The builder's status file reports, under `findings_for_other_pieces`, that
`ui-layer.mjs`'s `ui_combat_neutral` viewpoint dies on `aggro('deadwater-koor-nakh'): no such
entity` — `listEntities()` returns an eid that `aggro()` rejects — and that the tool's own
`try`/`catch` does not help *"because `tools/lib/browser.mjs` exits the process on a harness
throw"*. **That report is exact.** My own probe had a Node-side `try`/`catch` around the same
call and it took the whole run down at pass B5 anyway; the fix was to move the call inside
`page.evaluate` so the `catch` runs in the page. It is worth naming as a project-level defect
rather than a W1-21 one: **no tool in this repo can currently survive a harness error it has
already anticipated**, and every `try { await h.h(…) } catch` in `tools/` is decoration.

### 7.2 `journal-ui.mjs` JU8 still implements the pre-S35 clause

The round-1 verdict's secondary observation 1 said so and round 2 did not touch it.
`tools/analysis/journal-ui.mjs:199`:

```js
push('JU8', 'no map: unreachable AND non-existent (Q7)',
  nav.indexOf('map') < 0 && menus.indexOf('map') < 0 && mapThrew && ui.map_exists === false, …);
```

`AMENDMENT-W1-MAP-01` §3a struck the existence clause and replaced JU8 with nine assertions,
seven of them hard fails. The instrument still asserts the two conditions the amendment deleted —
that `openMenu('map')` throws and that `map_exists === false` — both of which are now *required
to be false*. So JU8 cannot pass at HEAD, and it cannot fail for a reason anybody should act on
either. Whoever lands an amendment owns the instrument: `INTENT-AUDIT-CHARTER` §6's own named
drift, *"a ruling amended without its enforcement amended is not fixed"*.

### 7.3 The exemption that was "paid for" with F6, and what F6 does not catch

`marker-scan.mjs` K1 is green at HEAD (0 hits, 1 declared exception, `--self-test` passes), and
getting there took widening `PLACEMENT_ROOTS` with `npcs/` and `audio/`. The builder declares
this as a judgement call and says it is paid for by a new rule F6, *"which fires on a coordinate
and a quest reference on the SAME record in ANY root … so widening the exemption list cannot
widen the hole."*

**F6 does not fire on the shape the exemption lets through**, and the builder's own self-test
says so. `tools/analysis/marker-scan.mjs:250`:

```js
['F6', { npcs: [{ id: 'a', quest: 'q-1', post: { pos: [1, 2, 3] } }] }, false],  // expected: NO HIT
['F6', { npcs: [{ id: 'a', quest: 'q-1', pos: [1, 2, 3] }] }, true],
```

The coordinate must be a **direct sibling** of the quest key. All 302 exempted hits are
`npcs[N].post.pos` — one level down — which is the first case, asserted silent. Today this costs
nothing, because I checked the data and no record in `quest-givers.json`, `faction-givers.json`
or `mainline.json` carries a `quest` key at all (a quest names its giver by id, which is the
id-only indirection §B asks for). The exemption is defensible on today's data. **The payment is
not.** Add `"quest": "q-x"` to a quest-giver record tomorrow and F6 stays silent by design, in a
root that no longer runs F2.
