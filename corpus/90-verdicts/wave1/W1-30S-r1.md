## 2. The mechanical read of the diff — the check that mattered

A move is honest if the moved body is the same tokens. Comparing by eye is how a changed `.075` gets
through, so I normalised whitespace out of both sides and compared the token streams directly
(`scratchpad/cmp.mjs`, reproduced in §9).

| moved body | from → to | token-identical? |
|---|---|---|
| the compositor (`_buildCompositor` body: HDR target, depth texture, the whole fullscreen shader, the ortho camera) | `renderer.js` → `render/post/composite.js` | **yes**, after the one rewrite the move requires (`this.worldTarget` → a local `worldTarget`, etc.) |
| the water surface shader (uniform block, `onBeforeCompile`, both injected GLSL programs, `customProgramCacheKey`) | `visual-foundation.js` → `render/water.js` | **yes** |
| `updateVisualFoundationFrame` | `visual-foundation.js` → `render/water.js` | **yes** |
| `bindWaterReflection` | `visual-foundation.js` → `render/water.js` | **yes** |

The GLSL strings are re-indented by two spaces by the move (they live at a shallower nesting level in
the new files). GLSL is whitespace-insensitive and `customProgramCacheKey` still returns the literal
`w1-30-water-ripple-reflection-v14`, so neither the compiled program nor Three's program cache can
see the difference. Not one literal, condition or operand changed in any of the four bodies.

**Structural checks around the move, all clean.** Exactly one importer per moved export, no dangling
reference to a moved symbol anywhere in `game/src` or `tools/`, no import cycle introduced
(`visual-foundation.js → water.js`, `sky.js → lighting.js`, and neither new module imports back),
and the module-level water state (`animatedWaterMaterials`, the four reflection variables) moved as a
unit to a module both of its importers resolve through the same specifier — so it is still one set,
not two.

### 2.1 The one thing in the diff that is not a move

`renderer.js`, in `render()`:

```js
-        const elev = Math.sin(((sim.env.timeOfDay - 6) / 24) * Math.PI * 2);
-        this.province.setNightFactor(1 - Math.max(0, Math.min(1, elev * 1.6 + 0.28)) * 1.6);
+        this.province.setNightFactor(1 - this.lightingFrame.day * 1.6);
```

This is a **deleted computation replaced by a cross-module read**, not an import rewrite. The plan's
third acceptance row says, verbatim: *"`git diff` on moved code contains only import/export rewrites
and whitespace. Any changed literal, condition or order is a plan violation and is reverted."* It was
not reverted.

The builder's defence is that the two are bit-for-bit equal, and **the builder is right**. `sky.js`
computes `day` from the same `hours` argument with the same operations in the same order
(`sky.js:213-218` against the deleted lines above), and `sky.apply(...)` is called with
`sim.env.timeOfDay` immediately before. I checked it rather than believing it: over 2,400,001 samples
of `timeOfDay` across `[0, 24]`, `Object.is(old, new)` held on every one, worst delta `0`. I also
confirmed there is no path that reaches the night-lamp line without `sky.apply()` having set
`lastFrame` — one call site, unconditional, one `return` in `apply()` and it is after the assignment;
and `this.scene.fog` is constructed once in the `Sky` constructor and never nulled, so the new
publication cannot throw on the sabotage path that sets `fogDensity = 0`.

So this is a zero-pixel change **today**. It is not a zero-risk change **tomorrow**, and that is the
finding: the province's night lamps now inherit `sky.js`'s `day` curve, and rewriting the
neighbourhood of that curve is W1-30B's first and second items (fog, then shadows, then the whole
lighting model). A B builder who retunes `day` will move the province's night lamps and have no way
to know. See F1.

## 4. The three registration points

### 4.1 Do they have live registrants, and does removal break the frame?

| point | registrant | what removal does |
|---|---|---|
| `registerComposite(mod)` | one — `buildCompositor(canvas.width, canvas.height)`, in the constructor | `this.worldTarget` / `this.compositeMaterial` stay undefined and `render()` dereferences `this.compositeMaterial.uniforms.uAO.value` — a loud `TypeError`, not a silent black frame. Load-bearing. |
| `registerPrePass(fn)` | one — `(frame) => this._renderWaterReflection(frame)`, in the constructor, called at the exact position the inline call occupied | `bindWaterReflection` is never called with a live texture, so `uWaterReflectionStrength` stays `0` and the water shader's `mix(esDepth, esReflection, (.25 + esGrazing*.50) * uWaterReflectionStrength)` collapses to `esDepth`. Every water surface loses its reflection. A visible, hashable frame change. |
| `setLightingFrame(obj)` | one — `render()`, immediately after `sky.apply()` | `this.lightingFrame` stays undefined and the night-lamp line throws. Load-bearing. |

All three are live and all three break the frame if removed. **But `setLightingFrame`'s consumer only
exists because the builder created it**, by the very edit that breaks the move-only row (§2.1). Under
a strict reading of "only import/export rewrites", nothing in the pre-seam renderer consumed a
lighting-frame object and this point would have shipped with zero registrants. The plan asks for both
properties and, for this one point, they cannot both hold. That is a defect in the plan, not
dishonesty in the builder — but it means the seam-liveness row and the move-only row are being
satisfied by the same line pulling in opposite directions, which is the shape of check the brief
warned about. See F2.

## 5. Would another child have to edit a file it does not own?

**Yes — two of them.** This is the check the plan hands the critic, and it is the one that fails.

**W1-30H.** H owns `render/spell-vfx.js` and `render/water.js`. Every decision about *when* and
*whether* the VFX prepass runs lives in `renderer.js`, which after this commit is W1-30A's exclusive
file. H cannot change prepass ordering, the particle/decal/mesh gate, or the pass lifecycle without
writing into A's file. The registration point that would have fixed this exists and is unused for the
purpose it was created for. (F3)

**W1-30D.** D owns `render/actor.js`, `render/models.js`, `render/lib/rigs.js` and
`render/rig-contract.js`, and its job is to replace primitive assemblies with authored glTF.
`models.js` publishes `export async function loadModel(id)`. But the player and every NPC mesh is
built **synchronously**, in `render/scene.js` (`scene.js:390` for the player, `:365` for the showcase
NPC, via `makeRiggedActor`) — and `render/scene.js` is declared **read-only to all children** by the
parent plan, and the ownership registry says nobody live has declared it at all. The seam published an
async entry point and no asynchronous seam to reach it: no model-ready hook, no deferred-swap
registration, nothing on `renderer.js` or `scene.js` that a promise can land in. D must edit
`scene.js` (read-only to everyone) or `renderer.js` (A's). (F4)

Two smaller ones, recorded rather than pressed. `this.three.shadowMap.enabled` and
`shadowMap.type = PCFSoftShadowMap` live in `renderer.js`; W1-30B's cascade work plausibly needs the
type. And the shadow *fit* — which the parent plan lists as a `renderer.js` collision — is in fact
already inside `sky.js` (`sky.js:139-159`), so the parent's own collision table was wrong there and
the seam correctly did not need to move it.

## 6. The four published registries: consumable?

`kits.js`, `lib/rigs.js` and `lib/lighting-recipes.js` each export a `register*(id, …)` alongside the
fail-closed getter, so a later child populates them **from its own file** without editing the
definition. That is the property that makes them registries rather than lists, and it holds.
`knownKits()` / `knownRigs()` / `knownLightingRecipes()` give the census something to read. Empty is
correct at this stage and all three fail closed on an unknown id, matching `worldMaterial` /
`regionArt` / `settlementArt`.

`models.js` is not a registry and does not claim to be — it is a stub `loadModel()` that throws
`not-yet-implemented`, exactly as the plan specifies, in a file W1-30D owns. Extending it means
editing it, and that is correct here.

One real gap: **nothing can be un-registered.** `register*` throws on a duplicate id and there is no
`unregister` or `reset`. This repository's whole sabotage discipline is a live off-switch that changes
shipping pixels (`setVisualFeature`); a registry that can only grow cannot host a null control, and a
module imported twice under two specifiers will throw rather than no-op. (F7)

## 7. How it landed — and this is the part to fix in the process, not the code

**For two commits, the branch could not boot.** At `3b43ec6c` and `380c374d` the constructor calls
`this.registerPrePass(...)` and `this.registerComposite(buildCompositor(...))` while
`registerPrePass`, `registerComposite` and `setLightingFrame` are **defined nowhere in `game/src`**
(`git grep` at those trees returns the two call sites and the comments, and no definition), and the
dead `_buildCompositor(w,h)` is still sitting at line 265. `new Renderer()` throws
`TypeError: this.registerPrePass is not a function`. The complete seam reached the branch only via the
merge `d88a3d29`, four minutes later, from the other side.

The builder's status says boot-check was green, and I have no reason to doubt that of the builder's
own working tree. What was *banked* was a half-written snapshot — the orchestrator's `git add -A`
caught the file mid-edit. That is Ruling O1's failure mode landing on the seam commit itself, and it
is worth saying plainly because the seam is the one commit in this tree where a partial bank is
maximally expensive: any agent that branched from `380c374d` got a game that does not start. (F5)
