## 2. Five findings the builder did not have

### D-1 (major) — the 3% silhouette guard does not do the job claimed for it. Deleting both the character's hands escapes it.

This is the axis the brief asked to be tested, and it breaks.

The guard's own docstring in `tools/visual/actor-hole-control.mjs` justifies the 3% figure this way:
*"3% sits well above the noise of a genuine seam fix (measured: −1.0% for the whole of this build's
change)"*. **The measured figure is −2.9%, not −1.0%.** The justification is wrong by a factor of
three, and it is wrong in the direction that makes the guard look safe. In fact:

- the shipped, legitimate fix moves the silhouette **−2.9%**;
- the arm-deletion cheat moves it **−3.3%**;
- the guard fires at **3.0%**.

So the guard separates "a correct fix" from "delete a limb" by **0.4 percentage points**, and the
shipped build sits **0.1 points** from tripping the guard on itself. The builder saw this and said
so — *"uncomfortably close to the guard"* — but drew the conclusion that a future change might trip
it, rather than that the guard's discrimination is already spent.

It is worse than close. This critic wrote three new controls (`/tmp/.../critic-guard-probe.mjs`,
patching a copy of the source tree, never a flag inside the instrument):

| critic control | crack px | silhouette drift | caught by the 3% guard? |
|---|---|---|---|
| shipped build | 178 | — | — |
| `hide-hand` (left palm, three fingers and thumb deleted) | **137** (−23%) | **−0.14%** | **no** |
| `hide-both-hands` (both hands deleted entirely) | **123** (−31%) | **−0.31%** | **no** |
| `debeak-head` (head crest plates) | 178 | +0.00% | inert — see §4 |

**Removing both of the character's hands improves the headline metric by 31% and moves the guarded
quantity by a tenth of the guard's threshold.** Hands are one of the two features the plan's own
item 5 says *"a person looks at first"*, and `no primitives in a shipped character` and the
proportions row both name digits explicitly. The plausible cheat the guard exists to stop is not
"delete a whole arm" — that is the conspicuous version. It is "delete the small expensive parts",
and that version walks straight through.

The first version of this critic's `hide-hand` removed only the palm entry in the segment table and
moved the silhouette 0.00%, because the fingers are built in a *separate* loop at `actor.js:505`. It
proved nothing and was strengthened, exactly as the builder had to strengthen its own. Recorded
because HAZARDS §0 is right that a control which fails to sabotage is indistinguishable from a build
that passes, and this critic hit it too.

**Remedy, and it is small.** The guard is on a *scalar* — total silhouette area — and a scalar cannot
notice that a specific part stopped existing. Replace it with a **per-part presence census**: at each
orbit stop, `rasterise()` already carries `owner[]` and the part label, so record the set of part
names that contribute ≥ 1 pixel anywhere in the run, and fail any build whose part set is a strict
subset of the baseline's. That is a dozen lines inside `classifyPockets`'s caller, it needs no new
threshold to argue about, and it catches deletion of *any* named part at any size. Keep the 3% area
guard as the second half — it is what catches `weld-arm-to-rib`, which adds rather than removes.

### D-2 (major) — the successor of the discriminator mistake is the held-object rule, and it has the bug the file warns about two lines earlier.

The builder was asked to find the successor of its own first mistake — a rule that excused four
floating crest cones. It is at `actor-orbit-holes.mjs:350`:

```js
const held = ring.some(([k]) => /^actor-held:/.test(k));
```

Directly below it, at line 351, the file states the correct principle and applies it:

```js
// Only the surfaces that actually ring the pocket in quantity decide: a single stray pixel of
// some distant part must not veto or create a crack finding.
const major = ring.filter(([, v]) => v >= Math.max(2, ring[0] ? ring[0][1] * 0.15 : 2))...
```

**The stray-pixel guard was applied to `major`, which feeds `allJointed` — and `allJointed` is
explicitly not gated, it is only reported. It was not applied to `held`, which is the surviving
gate.** One pixel of a sword or shield touching the ring of a pocket reclassifies that entire pocket
from `crack` to `bordered-by-held-object` and removes it from the count. The comment describing the
danger sits on the harmless branch; the load-bearing branch does not have the fix.

This is the same shape as the mistake the file records: an exclusion clause, principled-sounding,
that quietly removes real defects from the count. It is milder — a held object genuinely does have
sky around it — but the file's own standard for a discriminator is that it must not be able to
excuse a real defect, and a one-pixel veto can.

**Remedy:** compute `held` from `major`, not `ring` — one word:
`const held = major.some(...)` with `major` computed on labels rather than bones, or equivalently
gate on the held object's share of the ring exceeding the same 15% the file already chose. Then
re-run the full profile and report whether 2,204 moves. This critic did not re-run the full
5,760-frame profile after patching it, and says so rather than implying the number is unchanged.

### D-3 (major) — the builder's own reproduction command crashes at HEAD, so the headline number cannot be reproduced as written.

`orchestration/status/W1-30D.md` §8 gives:

```sh
node tools/visual/actor-hole-control.mjs --poses=default --angles=8 --distances=1.5 --baseline-ref=HEAD
```

It exits with `Error: control 'baseline' patched nothing — its anchor text has moved`, because the
work has since been committed and `HEAD:game/src/render/actor.js` is now byte-identical to the
working tree. The before/after that carries the whole claim — 9,254 → 2,204, or 1,858 → 178 at the
smaller profile — **cannot be re-derived from the documented command by anyone who reads the status
file.**

The correct baseline is `a1d24f58`, the commit before `4607cabe` ("W1-30D: the player's holes were
geometric in five places"). With it, the numbers reproduce exactly. **Remedy:** pin the ref in the
status file and in the tool's default, and have `--baseline-ref` refuse a ref whose blob equals the
working tree with a message that says *"this ref is not a baseline"* rather than *"the anchor moved"*.

### D-4 (major) — the plan's orbit gate is binary and it is not met; the tool's own verdict on the shipped build is FAIL.

The bar row reads *"across 144 orbit frames, **zero** background pixels appear inside the body
silhouette"*, and `hard fails` includes *"a transparency regression at any orbit stop"*.
`actor-orbit-holes.mjs` computes `verdict: totalHole === 0 ? 'PASS' : 'FAIL'` and returns **FAIL** on
the shipped build, at both profiles. A 76% reduction is a real and well-evidenced improvement; it is
not the gate. This verdict does not treat the residual as fabricated — the builder is right that
part of it is a forearm passing near the hip — but the row as written is unmet and no amendment has
been filed to change it.

**Remedy:** either close the residual, or file the amendment. The honest amendment is available and
the builder half-wrote it: the row should bind on *crack pixels attributable to a joint or an
ornament* rather than all enclosed background, and it should state the attribution floor the builder
found (`~200 px at the 640-frame profile`) as a declared limit of the instrument rather than as a
footnote. An unamended binary row that the owning child cannot meet is how a dashboard goes green
over an unmeasured thing.

### D-5 (minor, and it corroborates the build) — one of this critic's controls was inert, and the reason is that the crest fix is real.

`sink-crest` — burying the dorsal crest further inside the body and shrinking it 65% — produced
numbers **identical to the shipped build to the pixel** (178 crack px, 53,075 px silhouette). The
patch applied; the output did not move. That is because the crest is already fully interior to the
skinned surface, so moving it further in changes no exterior pixel. The control proves nothing about
the guard, and it is reported as inert rather than as a pass — but it is independent confirmation
that defect #2 in the builder's list (four cones floating up to 35 cm off a 14 cm-deep back) is
structurally closed, not cosmetically hidden.

## 3. What a person sees — the gate that actually decides

**288 stills and 400 motion frames were captured on real hardware** for this verdict: RunPod
NVIDIA L4, `ANGLE (NVIDIA, Vulkan 1.4.303)`, marked `HARDWARE — valid for appearance claims`, at
the `full` Deck profile, seed 20260814, 960×540. Cost $0.054. This closes the builder's own
*"no human has looked at these characters"*.

**The transparency defect does not reappear at the stops rendered.** At the two mandatory character
close-ups and across the motion sequences, no sky is visible through the body. That is a genuine and
significant improvement and it should be said plainly.

**And the characters do not read as characters.** The player close-up
(`docs/shots/2026-08-14-w1-30de-critic/char-player__t1300__clear.jpg`) is a white-plastic segmented
figure: the legs are two smooth pale tubes with no readable feet, the arms do not separate from the
torso at all, there is no skin tone, no face, and the hands — the thing §5 of the plan calls one of
the two features a person looks at first — are not visible as hands at 2.6 m. The NPC
(`char-npc__t1300__clear.jpg`) is the same body reading as a stack of white capsules under a brown
dome helm. Both carry a greatsword that is a flat brown plank and a shield that is a flat polygon.

The plan's gate is *"naive judges answer 'is this a character model from a game you'd play?' yes
≥ 70%"*. No naive pack was run, and this critic will not manufacture a number for it — but the
frames are in the tree and the honest statement is that the gate is nowhere near, which is what the
builder said in advance. **This is `Ruling W2` territory: the piece has improved a statistic and
that is not the same as the thing being good.**

**Motion is captured and it evidences almost nothing.** All twelve sequences ran, 12 ok / 0 red, 400
frames, deterministic (30 distinct frames per 30-frame sequence). But in the Deck's motion setups the
character occupies roughly forty pixels of frame height, so the contact sheets
(`motion-walk-contact.jpg`, `motion-attack-light-contact.jpg`) can show that the sword arcs and the
body translates and cannot show whether a knee bends correctly or a foot slides. **The 12 motion
sequences as configured are not an instrument for judging character animation**, and that is a
`W1-30V` finding rather than a `W1-30D` one — but it means the animation axis below is scored on the
absence of the work, not on frames that failed.

## 5. Biggest gap and its remedy

**GAP-W1-w1-30d-guard-misses-part-deletion** — the anti-gaming guard on the character defect metric
is a scalar area check that cannot see a named part disappear, and deleting both of the character's
hands improves the metric by 31% while moving the guard's quantity by 0.31% against a 3.0% threshold.

Every future claim about this character rests on a metric whose only anti-gaming guard has been
shown, on a copy, to miss the cheapest real mutilation. The remedy is the per-part presence census in
D-1: it is a dozen lines, it needs no new threshold, and it is strictly stronger than the number it
supplements. Land it, re-run the six existing controls plus `hide-both-hands`, and the metric becomes
trustworthy again.

## 6. What this critic could not do

- **No Protocol A pack, no naive character pack, no silhouette-readability pack.** `RI-VIS06`
  Protocol A requires a pack-builder who is not the judge; this critic is one agent and building the
  pack it then judged would be the coupled-yardstick failure `ARBITRATION` S51 convicts. The frames
  exist in the tree for a pack-builder to use. Protocol A therefore **did not run in this round**,
  and under the evidence standard's own clause a wave in which zero Protocol A pairs ran **caps
  FIDELITY at 7** — which is below nothing this verdict awards, so it changes no number here.
- **No 24-stop × 3-distance orbit was rendered on hardware.** The Deck's `char-player` and `char-npc`
  setups are one yaw each; the 144-frame orbit is a separate rig this critic did not build. The
  transparency finding in §3 is therefore *"clean at the stops rendered"*, not *"clean at 144 stops"*,
  and it is stated that way deliberately — that distinction is the exact one the owner's complaint
  turned on.
- **The full 5,760-frame profile was not re-run** after diagnosing D-2, so this verdict does not
  claim to know how much of the 2,204 the held-object bug is hiding.
- **`beast` and `undead` families** were not re-measured; the builder's 640-frame figures are taken
  as reported and are not independently confirmed.
- **`game/index.html`'s import map**, edited outside the builder's owned paths, was checked and is as
  described: additive, and `grep -rn "from 'three'" game/src` returns nothing. Not a defect.
