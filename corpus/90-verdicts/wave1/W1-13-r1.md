## 1. Do souls survive a mid-death save? **No. 4,200 in, 0 out.**

`tools/harness/critic-w1-13-a.mjs` → `artifacts/W1-13-r1/mid-death-save.json`. Every assertion reads
the **live world** after the load (`getDeathState`, `getPlayerStats`), never the blob — the sibling
save critic showed why auditing the blob is a fixed-point test.

| Trial | Save taken | Reload | Recoverable |
|---|---|---|---:|
| T1 | **while the death surface is up** | `page.reload()` — a real browser restart | **0 / 4,200** |
| T2 | *control:* after the respawn, bloom outstanding | same restart | **4,200 / 4,200** ✓ |
| T3 | while the surface is up | same-session `loadState(blob)` | **0 / 4,200** |

The control is what makes this a finding rather than a mood. `RI-JRN06` M-D16 as worded passes: the
bloom survives a rest, a region change, a named-state load, a blob restore and a real IndexedDB
round trip. Take the save 150 frames earlier and it does not.

**Mechanism.** The blob correctly carries `death.bloodstain = {souls: 4200}` **and**
`character.hp = 0`. `DeathSystem`'s in-flight state — `active`, `deathFrame`, `controllableAt` — is
not durable, and `loadState(blob)` clears `lastHp`/`lastGrounded` but does not reconstruct the
surface. So on the very next frame:

```
observe()  →  hp <= 0 and !this.active  →  die(cause: 'combat')
die()      →  prev = the 4,200 bloom
           →  stainsLostToSecondDeath++
           →  sim.quest.death.bloodstain = { souls: sim.progression.soulsHeld }   // 0
```

The artifact records exactly this: `after_1_frame.deaths_this_session: 1`,
`stains_lost_to_second_death: 1`, `bloom.souls: 0`. D16's second-death branch fires against a death
that never happened, and the player loses 4,200 souls to pressing *Continue*. This is `RI-JRN06`'s
own **"How we lose" #2** arriving through a different door — the bloom *is* persistent; the load
re-kills you.

**Why it is not the named gap, and it was close.** Nothing in the shipping game calls `writeSave()`
today — the only callers are the harness and probes — so a player cannot currently reach the state.
It arms the instant autosave or save-on-rest lands. It is `secondary_observations[0]` and the remedy
is in `path_to_ten`.

`tools/journey/jrn06-death.mjs:313`:

## 5. Placement: three of four branches never fire

`placeStain()` has four rules. The builder's session reports `placement_rule: death_point` on
**20 of 20** and a `0.000 m` offset on every one, because every death was reached by `teleport` onto
flat standable ground.

| Rule (`RI-PRG04` §6) | Fires? |
|---|---|
| Sealed / one-way → relocate toward the hearth | ✓ 14.5 m (builder), 80.0 m (walked) |
| Death point, clamped within 2.0 m | never exercised — nothing needed clamping |
| **Fall / hazard → the last grounded position, not the bottom** | **never fires** |
| **Boss arena → outside the fog gate** | **degenerate at the centre** |

**The fall rule is unreachable.** I dropped the body 90 m and killed it. It recorded
`cause: 'combat'`, `placement_rule: 'death_point'`. `traversal.js:401` sets the player state to
`DEATH` on the landing frame, and `_inferCause()` only returns `'fall'` while the state is `FALL` —
so by the time `_deathTick()` runs, the evidence is gone. `_inferCause()` can only ever return
`'fall'`, `'hazard'` or `'combat'`, which also makes `placeStain()`'s `cause === 'drown'` branch
dead code. `RI-PRG04` §6's *"bloodstain is placed at the last grounded position before the fall, not
at the bottom"* is unimplemented in effect.

**The fog gate degenerates at exactly the centre.** The push-out normalises by
`Math.hypot(dx, dz) || 1`:

| Death offset from arena centre | Bloom lands | Outside r=26? |
|---:|---:|---|
| **0 m** | **0 m** | **NO** — and the record still reads `outside_fog_gate` |
| 0.001 m | 29 m | ✓ |
| 0.5 / 5 / 20 m | 29 m | ✓ |

Measure-zero, and the arenas do not reseal in this build, so **HF7 is not triggered** — but the rule
*reports* it did the thing it did not do, which is the shape that survives a review.

## 6. THE SINGLE BIGGEST GAP

> **`GAP-W1-hearth-levelup-gate-reads-a-method-that-does-not-exist`**
> `subsystem_path: progression.bonfire.function` · severity **blocking** · size **S**

`RI-PRG04` §1, binding: *"**Level up** — spend souls, +1 attribute per level, `RI-PRG01` curve.
**The only place levelling is possible.**"*

`critic-w1-13-f.mjs`, measured live at three wells:

| Well | Registry says | `openMenu('levelup')` | UI mode after |
|---|---|---|---|
| `hearth-archon` | `standing_at: hearth-archon` | **REFUSED** | `world` |
| `hearth-lilmoth` | `standing_at: hearth-lilmoth` | **REFUSED** | `world` |
| `hearth-gideon` | `standing_at: hearth-gideon` | **REFUSED** | `world` |
| **control:** `setAtHearth(true)` | — | **OPENED** | `levelup` |

The refusal message is the build's own: *"the level-up screen exists at a HEARTH only (RI-UIX03
L1)"* — thrown while standing on the basin, one frame after a successful `restAt()`.

**The mechanism.** `game/src/engine.js:2011`:

```js
atHearth: !!(this.hearths && this.hearths.atHearth && this.hearths.atHearth(this.sim))
          || !!this.sim._uiForceHearth,
```

`HearthSystem` (`game/src/sim/hearth.js`) defines `list`, `get`, `count`, `nearest`, `at`, `gateAt`
and `menu`. It does **not** define `atHearth`. The `&&` short-circuits on `undefined` at every one of
the 29 wells, and the only writer of the second disjunct is `setAtHearth()` — a harness override with
no in-game counterpart. `_spendSouls()` has exactly one producer (`ui/system.js:322`, inside
`case 'levelup'`), so **souls have no sink anywhere in the running build.**

**Why it matters.** The player banks souls, risks them, dies, walks back over ground they now know,
finds the bloom, touches it, gets exactly 4,200 — and cannot spend one. Everything this piece
protects so carefully has nowhere to go.

**Remedy — one method body:**

```js
// game/src/sim/hearth.js, in HearthSystem
atHearth(sim) { return !!this.at(sim.player.pos[0], sim.player.pos[2]); }
```

`at(x, z)` already exists, already tests each well's own `interact_radius_m`, and already backs
`listHearths().standing_at`. The registry was right; only the name the UI calls was missing.

**Acceptance:** `critic-w1-13-f.mjs` reports `levelup_reachable: true` at all three wells with **no
`setAtHearth()` call anywhere in the probe**, and `false` 50 m off the basin; a `level_up` trace
event fires from a well and from nowhere else; `soulsHeld` falls by exactly `soulsToNextLevel()` and
`level` rises by 1.

## 7. The named-NPC guarantee: it holds, for a reason other than the one demonstrated

I attacked S5 on **both triggers** (rest and death) and through **both routes** to the flag.

`game/data/world/respawn.json` states its own producer in words:

> `"_never_respawn_entity_flags_note": "Set per SPAWN (engine.spawn(id, x, z, {named: true}))"`

`engine.spawn()` reads `opts.as` and `opts.yaw`. It copies **none** of the six flags.

| Route | `named` | `merchant` | `questActor` | `trainer` | `boss` | `unique` |
|---|:-:|:-:|:-:|:-:|:-:|:-:|
| **`spawn(id, x, z, {flag:true})`** — what the data file documents | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |
| `__HARNESS.setEntityNamed()` — what the builder's fixture uses | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |

Six of six **stood back up** after a hearth rest *and* after a player death when flagged through the
documented route. That is `RI-MTH07` §A's **orphan predicate** — *"a rule that decides something;
nothing ever supplies it world state; only a critic hand-feeds it"* — and it is precisely what
`RI-MTH07` method 3, the hand-feed audit, exists to catch. The builder's headline —
*"the classification file was emptied on purpose and the boss stood back up, proving the rule is
read rather than hard-coded"* — is **true and insufficient**: it proves the predicate is *read*, and
says nothing about whether the world can *write* it.

**Does the guarantee hold today? Yes — and not because of that branch.** Three things hold it:

1. **`sim.npcs` is a different array.** Every merchant, trainer and quest-giver lives there and no

2. **`never_respawn_ids`** protects the two bosses by statblock id. That branch works.
3. **The shipped province's default state contains zero entities**, so there is currently no named

So **HF3 is not triggered** — but M-D5 scores **0**, fail-closed, under `RI-JRN06`'s own CONSUMPTION
clause. The moment W1-12 places a hostile roster and a quest places a named actor the documented
way, this becomes an AR-1 hard fail in someone else's verdict. It is three lines from fixed and it is
folded into the named gap's remedy.

## 11. What this piece got right, so a harsh number does not erase it

The loop **works, walked, end to end**, and I checked it myself rather than taking the report. Souls
conservation is exact when the filtered rows are put back. The single-stain rule is **structural** —
one field, not a list — and the builder said so instead of faking a break, which is the harder and
better answer. The death surface is **drawn**, proved by a 124× pixel swing against an alive control
rather than asserted. S7 holds in both directions. **Nine of nine** of `RI-PRG04`'s own predicted
failure modes were avoided — including the two most likely, dense wells and warp-between-wells.

And the builder found, fixed and *reported* five defects in its own probes, a sticky death camera its
own across-death diff caught, five wells sitting on travel quays, and a cross-piece regression that
had silently deleted **THE DRY WELL's entire drawback** from every loaded session — rather than
shipping the passing number. That is the behaviour this loop is supposed to produce.

The failure is a tenth thing `RI-PRG04` did not predict: the checkpoint heals you, refills you,
re-grows the marsh, moves the clock, poisons you slowly and puts you back on your feet — and cannot
take your souls, because the gate calls a method the hearth system never grew. One method body.
