### 1.3 "Allocation is a literal 0 B/step" — **SURVIVES AS A BOUND, NOT AS A LITERAL ZERO**

**First, the instrument.** The builder's mechanism claim is right and its wording is wrong. My
own self-test, both ways, on both trees (`critic2-alloc-slope.json → self_test`):

| Self-test | CDP defaults | `includeObjectsCollectedByMinorGC/MajorGC: true` |
|---|---|---|
| 100,000 **escaping** `{a,b,c}` literals (retained in `window.__sink`) | **28.98 B each** | 38.22 B each |
| 100,000 **dying** `{a,b,c}` literals (never retained) | **0.073 B each** | 9.16 B each |

The defaults do not under-report *escaping* objects at all — they under-report **dying** ones, by
**125×**. Per-frame garbage in a game loop is dying garbage, so the correction is real and large.
But `alloc-probe.mjs`'s shipped self-test prints
`29.13 B per escaping {a,b,c} literal (expect ~28-32) — OK`, which is the number the defaults
already get right: **the self-test would pass with the flag it exists to verify turned off.**

**Second, the true round-1 figure.** I built a `git worktree` of round 1's judged commit
`8714e38` and ran the *same* critic-owned probe against it with the flags on
(`critic2-alloc-prefix.json` vs `critic2-alloc-slope.json`):

| Fixture | round-1 tree, flags ON | current tree, flags ON | round-1 critic reported |
|---|---|---|---|
| F1 fen (`swamp_canopy`) | **29.64 B/step** | **−0.88 B/step** | 0.98 |
| F5 dungeon (`dungeon_primary`) | **30.21 B/step** | **−0.35 B/step** | 1.73 |
| F4 six enemies (`arena_flat` + 6) | **90.96 B/step** | **+0.069 B/step** | 0.78 |

So round 1's figure was under-reported by **30–117×**. **The true "before" was 30–91 B/step, not
~1 B/step**, and the improvement is correspondingly larger than the remediation claimed. (Both
columns use one `stepFrames(N)` call at N and at 2N so the per-call constant — including the
render `stepFrames` does at the end — cancels in the slope. My first pass chunked the steps and
measured 7.6–25.1 B/step of *render*; that wrong measurement is kept in
`critic2-alloc-current.json` rather than hidden.)

**Third, the "literal zero". It is not literal, and the tell is in the tool's own printout.**
At the builder's step count:

```
F1: SIM PATH slope 9828 B @ 120000 steps - 10344 B @ 60000 steps = 0 B / 60000 = 0 B/step — PASS
```

9,828 − 10,344 is **−516**, not 0. The reported zero is `max(0, slope)`. And at a step count I
chose, the same tool on the same tree prints:

```
F1 fen:      SIM PATH slope ... = 0.0034 B/step — budget 0 B/step — FAIL
F5 dungeon:  SIM PATH slope ... = 0.015  B/step — budget 0 B/step — FAIL
```

`alloc-probe.mjs --steps 20000` **fails** the two fixtures `--steps 60000` passes. My own probe
at 20,000 steps gives −0.88 / −0.35 / +0.069 B/step: noise, of both signs.

**Ruling.** Sim-path allocation is at or below this instrument's resolution (its own printed
baseline is 0.20–0.57 B per empty-loop iteration) and is a large, real improvement on
30–91 B/step. `RI-PLT01` P4's *literal* zero is not demonstrable either way at this resolution,
and the report's sentence "Zero at both step counts, so it is a literal zero and not a slope of
noise" is not reproducible here. I score M4 **pass on the bound** and record the clamp and the
step-count dependence under `RI-MTH04`.

### 1.4 "The trace record is built outside the step, enforced by a counter that throws" — **SURVIVES**

Demonstrated at runtime, not read. I queued an input event whose `move` property is a **getter**,
so the read fires from inside `stepFrames()`, and called `snapshot()` — which builds a §5 record —
from inside it (`critic2-r5-reanchor-guard.json → stepdepth_guard`):

```
"snapshot-threw: TRACE RECORD BUILT INSIDE THE FIXED STEP. RI-PLT01 §C.3 requires the frame
 record to be built outside the simulation step: it allocates ~2 KB, and a step that allocates
 is a GC pause during a boss win"
"random-threw: DETERMINISM VIOLATION: Math.random() was called inside a fixed simulation step…"
"date-threw:   DETERMINISM VIOLATION: Date.now() was called inside a fixed simulation step…"
```

Three times, once per step. Outside a step all three succeed
(`outside: {random: true, date: true, snapshot: true}`), and the same getter fired three times
during `queueInputs` — outside a step — and was allowed. The discrimination is correct.

### 1.5 "R5 is a real fix, not the rung reshaped around the build" — **SURVIVES, with the residual named**

I did not run the ladder for this. I re-implemented R5: warm-up 30 vs 90, a 600-frame scripted
window, my own re-basing of all three absolute frame indices (`f`, `events[].f`,
`enemies[].state_entered_f`, the last with a `pre-window` sentinel), `rng` dropped, and
`enemies[].anim_frame` **compared** (`critic2-r5-reanchor-guard.json`):

| Configuration | differing fields over 600 frames |
|---|---|
| with `reanchorFreeRunning()`, one enemy | **`{}` — none** |
| **without** the re-anchor, same fixture | **`{"enemies[].anim_frame": 198}`** |
| with re-anchor, no entity at all (round 1's counter-example) | **`{}` — none** |

Two things follow. The rung still has teeth — remove the re-anchor and it fails on exactly the
field round 1 said must not be excluded. And the re-anchor is a **simulation** mutation, not a
trace edit: `getStateHash()` moves `f83383eb…` → `8b09fbe7…` across the call, the mutation
survives a save/load round trip (reloaded hash identical), and the clock runs on from the new
phase (`anim_frame` 40 → 43 over three steps). Round 1's own third option — "make the scenario
contract re-anchor free-running entity animation at the frame the scripted window opens" — is
what was built, and `AM-W1-00-01` is withdrawn in its own file with its three defects conceded.

**The residual, recorded not scored.** After the re-anchor, `anim_frame` inside the window is a
function of the seeded phase and the frame offset alone, so R5 can no longer *detect* a
warm-up-dependent divergence in any clock the re-anchor normalises. That is defensible — the two
runs really are in the same state, so the invariance claim is true rather than faked — but R5's
discriminating power over free-running clocks now depends on the build honouring a contract,
and `HARNESS.md` §3 accordingly lists `reanchorFreeRunning` as "strongly expected".

## 2. The hard fail this round: `RI-JRN05` M5 / HF1

`RI-JRN05` M5, verbatim: *"from the loaded state, run an identical 600-frame scripted input
script against (a) the never-saved session and (b) the loaded session, both at the same seed.
Compare `body_sha256` of the two traces."* Threshold: *"Identical for 5/5. **Hard fail: any
divergence** — it means the RNG draw counter or a derived cache was not restored."*

I ran exactly that, seed 4711, with an **identical 120-frame pre-roll on both sides** so the only
difference between them is the save and the load (`critic2-m5-postload.json`):

```
control body_sha256 : 5d0830f9b9e3ea715402…
loaded  body_sha256 : d52edb76370c7c08b75c…
identical           : false
differing fields    : { "enemies[].prev_state": 219 }   (of 600 frames)
first divergence    : frame 0 — control "IDLE", loaded null
```

The cause is in the saved entity record itself, which the same artifact captures:

```json
{"id":"inf_trash","eid":"e0","pos":[0,0,7],"yaw_deg":180,"hp":412,"poise":22,
 "alert":100,"alert_state":"AGGRO","state":"FACE","anim_frame":47,"anim_phase0":23,
 "anchor":[0,0,7],"stagger":false,"stagger_in_frames":0,"state_entered_ago_frames":96}
```

`state`, `anim_frame`, the seeded `anim_phase0` and even `state_entered_ago_frames` are all
carried. **`prev_state` is not.** `world.entities` is a **`durable`** path in
`game/data/save-manifest.json`, and `prev_state` is on no volatile list — the manifest's own
rule V1 reads *"The volatile list is CLOSED. A field that differs across a round trip and is not
on it is a defect. Moving a field onto it to make a test pass is falsification under RI-MTH04,
not a fix."*

**It is not a regression.** I pointed the same probe at the `git worktree` of round 1's judged
commit `8714e38` (`critic2-m5-postload-prefix.json`) and it reproduces exactly: same field, same
219 frames, same `"IDLE"` → `null`. Round 1 reported *"M5 post-load divergence: PASSES"*. Its
re-run compared a window in which the field happened not to differ, and the check has been green
in the corpus ever since — the same shape of false pass that the round-1 verdict itself was
written to expose.

**`RI-JRN05` HF1 fires on its M5 clause. The item is capped at 2 and its status is FAIL.**

## 12. The `sim_units` corpus hole — **verified; a corpus hole, not a build failure**

`RI-PLT01` §A rule S\* defines
`sim_units = measured_sim_ms × (cpu_index_reference / cpu_index_thismachine)` and says "the
reference is the declared `phone-mid` class". I grepped the entire corpus for a numeric
`cpu_index_reference`. The only hit anywhere in `corpus/` is the definition itself:

```
corpus/85-platform/RI-PLT01-frame-budget.md:127:  …(cpu_index_reference / cpu_index_thismachine)…
```

`phone-mid` appears elsewhere only as a device-class *label* (`RI-PLT01` §A/§C, `RI-PLT02` §B.1,
`RI-PLT03` §C.1). No numeric value exists in `corpus/00-doctrine/constants.json`, in any
`corpus/85-platform` data file, or anywhere else in the tree.

**Ruling.** The builder's report is right: `RI-PLT01` **M3 (8 points) is unscoreable on any
machine**, real hardware included, and so is `RI-PLT03` P6, until the constant is declared.
`calibrate.mjs` refusing to emit an invented number is the correct behaviour — it is
`RI-PLT01` M15's honesty rule applied to itself. It does **not** change the score:
`SCORING.md` §1.1 is explicit that unmeasurable is **0**, fail-closed, whoever's fault it is.
M3 scores 0 and the 8 points are lost.

Filed as `corpus_extended` (`reason: corpus_hole`) and as an `arbitration_question`, with the
remedy stated: declare `cpu_index_reference` for `phone-mid` in `RI-PLT01` §A as a number
measured by `calibrate.mjs`'s own workload on an attested `phone-mid` device, with its checksum.
I have **not** invented the constant; a critic that guessed it would be fabricating the very
measurement `RI-MTH04` exists to prevent.
