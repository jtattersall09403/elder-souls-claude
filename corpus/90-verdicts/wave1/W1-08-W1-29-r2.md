## 7. The biggest gap — a calibration that outlives its pad, again

**`GAP-W1-input-calibration-outlives-its-pad-on-disconnect`** — `input.gamepad.lifecycle` — severity
**major**.

Round 2's build fix is real and I re-derived it. `_applyButtons()` now reads

```js
const perm = this.calibrationResult && this.calibrationResult.id === st.id ? this.calibrationResult.map : null;
```

and with my own driver, on the shipped build: calibrate `"Some Unknown Pad 9000"` through all six
prompts (`{0:roll, 1:block, 2:light, 3:interact, 4:menu, 5:lock_on}`), unplug it, plug in
`"Xbox 360 Controller (XInput STANDARD GAMEPAD)"` → index 0 fires **`interact`**, index 5 fires
**`light`**. Correct. The builder's headline is true.

**It guards the *completed* calibration. Nothing guards the one in progress.** `this.calibration` is
instance state with no pad id on it, `_beginCalibration()` is triggered from `_adoptPad()`, and
**`_dropPad()` never clears it**. `poll()` then runs `_calibrationPoll(st)` against whatever pad is
*currently active* — which need not be the pad the calibration was begun for.

Measured on `dcf1d36`, no instrument in the loop, my driver, delete-the-fix both ways:

| Step | shipped build | with the one-line fix |
|---|---|---|
| stranger arrives, answer 2 of 6 prompts | prompt 3/6 | prompt 3/6 |
| **unplug it** (`n_pads: 0`) | **`calibrating: true`, prompt still 3/6** | **`calibrating: false`** |
| plug in a **standard** pad, press index 0 | **`[]` — nothing** | **`interact`** |
| …index 1, 2, 3 | **`[]`, `[]`, `[]` — a dead pad** | — |
| the prompt after those four presses | **advanced 3/6 → 5/6** — the standard pad's presses were eaten as the stranger's calibration answers | — |
| finish the sequence on the standard pad | `result_id: "Xbox 360 Controller (XInput STANDARD GAMEPAD)"`, map `{0:roll, 1:block, 2:light, 3:interact, 4:menu, 5:lock_on}` | — |
| press index 0 / 4 / 5 | **`roll`** / **`menu`** / **`lock_on`** | `interact` / … / `light` |
| after 600 further frames | still calibrating; **it never times out** | — |
| press index 5 on the standard pad | — | **`light`** |

**In a player's hands.** The owner plugs the GameSir X2s in its DualSense-like HID mode — the mode
`pad-quirks.json` exists for — and the game starts the six-prompt calibration, which is correct. The
USB-C connector jogs loose, which is the *precise* scenario `M-P12` was written for and which that
check passes on. They re-seat it, or reach for a normal pad. **The pad is dead**: no button does
anything. The in-fiction prompt (*"Take it on the shield."*) stays on screen forever. If they persist
and press their way through it, they end up with a standard pad on which **A rolls instead of opening
the door** — the exact symptom this round's commit message says it fixed, reached by an ordinary
disconnect instead of an exotic swap.

**Not an unrecoverable loss of control, and I checked rather than assumed.** With the calibration
stuck I read the touch layout and drove it: all sixteen actions are still there and `light` still
fires. On a handheld the glass is live, so `M-N5`/HF10 is *not* triggered. It is a dead pad and an
undismissable prompt, on the device the owner tests on.

**The fix, which I wrote and ran:** clear an unfinished calibration when its pad drops.

```js
// game/src/input/gamepad.js — _dropPad(), after this.pads.delete(idx)
if (st && this.calibration && !this.calibration.done) this.calibration = null;
```

With it applied in the page, the same sequence gives `calibrating: false` after the unplug and
`interact` / `light` on the standard pad's indices 0 and 5. **Delete-the-fix reproduces the defect
exactly**, in both directions, which is the property this project requires and which the builder
itself demonstrated for its own fix.

**Acceptance:** a `--self-test` leg that begins a calibration, disconnects mid-sequence, connects a
`mapping: 'standard'` pad and asserts index 0 fires `interact`; and `M-P15` extended to run its
sequence a second time with a disconnect at prompt 3.

**Why this and not `M-P20`.** M-P20 is red, declared, and belongs to a typography round that moves
every screen. This is a two-minute change that turns the owner's own controller dead, it is in the
lifecycle block whose entire purpose is "does not lose the player", and — the part that decides it —
**it is the same class of defect the round's headline fix was for, one layer up, and the round's own
repaired instrument walked straight past it** because `M-P15` only ever calibrates and never
disconnects.

## 10. What is genuinely very good, so the next round does not regress it
