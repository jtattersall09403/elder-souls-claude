## 0. The number the brief gave does not match what the tool prints today, and that is not a new bug

The brief says *"121 pieces that are FINISHED BUT UNJUDGED."* Running `node tools/dispatchable.mjs` right
now prints **126**. Both are real; neither is stable; here is why they differ.

**The regex defect the brief warned about is already found and already fixed** — by a different agent,
hours before this dispatch, at commit `f0946995` (2026-08-14 12:16:02Z), which the diff and commit message
confirm did exactly what the brief describes: the old key —
`(id.toLowerCase().match(/^(w\d+-[a-z0-9]+)/) || [, id.toLowerCase()])[1]` — stopped at the first hyphen
after `w<N>`, so a two-word piece id (`W1-LIBRARY-MARTIAL`, `W1-ATTR-SCALE`, `W1-PROSE-TICS`) was looked up
under its first word only, which exists nowhere, so all three read unjudged while their real verdicts (5.4,
0, 4) sat on disk. The fix, `verdictLookupKey()`, strips only a genuine trailing `-r<N>` round marker and
otherwise keeps the full multi-hyphen name, matched for **exact** equality — deliberately not prefix
matching, because prefix matching would credit standalone `W1-08` with the *joint* `W1-08-W1-29-r2`
verdict, which is a real, live, separate task. The same commit **swept the inverse error** the earlier audit
had flagged as its own likely blind spot: 22 rows in the *done-and-judged* bucket were reading as already
judged off an unrelated or superseded round's verdict (`W1-17-act5-r2` was reading plain `W1-17`'s score of
5, when its real predecessor `W1-17-act5-r1` scored FAIL 3/10 and round 2 has no verdict of its own). All 22
now correctly report unjudged. `node tools/dispatchable.mjs --self-test` passes 6/6 arms when re-run here,
including the 4 new `verdictLookupKey` arms, each of which is checked against the **real** corpus rather than
a fabricated fixture (HAZARDS.md §0's warning about self-tests that only agree about a false premise).

**126 vs 121 is population growth, not miscounting.** `git log f0946995..HEAD -- orchestration/status/`
shows 43 status files touched since the fix landed; cross-referencing those against the current 126-row
list finds **11 pieces that genuinely crossed from in-progress into complete-with-no-verdict** in that
window: `W1-11-builder`, `W1-18-builder-codex-20260810`, `W1-DLG-WORDS`, `W1-THORN-PLATES`,
`GIT-INTEGRATION-SCHEME`, `PARTIAL-REVERTS-20260814`, `RECOVERY-20260814`, `RI-VIS06-PROTOCOL-A`,
`SPLIT-TRIAL`, `plan-review-w1-dlg-topic-web`, `plan-review2-w1-dlg-topic-web`. The rest of the
126-vs-96-at-audit-time delta is almost entirely rows that existed at audit time but were only named
*collectively* in `UNJUDGED-TRIAGE-2026-08-14.md`'s prose (e.g. "Plan-loop rounds (20)" lists 20 representative
ids, not necessarily all 24 that exist) rather than individually — a caveat, not a contradiction; see §5.

**Ownership.** `node tools/ownership.mjs --for tools/dispatchable.mjs`: nobody live has declared the file
itself. `W1-20-r3-remediation` (live, `in_progress`) lists it in `files_claimed`, but for an unrelated
faction-gate fix, and has not yet touched it (`files_touched` is only its own status file). Left the tool
alone rather than write into a file a live sibling is about to touch — and it does not need editing: the
fix is landed, tested, and its remaining exact-match limitation is by design (see §1).
