## What was actually broken (the durable fix, in `tools/ownership.mjs`)

1. **`status` vs `state`.** 78 of 452 status files record completion in a field literally named
   `"status"`, not `"state"`. The shipped tool read only `j.state`, so every one of those 78
   displayed as state `?` and counted live regardless of what it actually said — 20 of them say
   `"status": "done"`, 31 say `"complete"`. Fixed: read `state`, fall back to `status`, test both.
2. **No word boundaries on compound machine-generated state strings.** `"builder_delivery_complete"`
   never matched `/complete/i` at a word boundary the way plain `"complete"` does (underscore is a
   word character), so it read as non-terminal. The naive fix (bare substring match) would have
   been worse: it would wrongly match `"complete"` inside `"builder_delivery_incomplete"`. Fixed by
   normalising `_`/`-` to spaces before testing, proven correct in both directions by the self-test.
3. **`built_awaiting_critic` — this dispatch's own named calibration case.** A builder handed to a
   critic has stopped editing its own claimed files by definition; a critic reads and judges, it
   does not write source. Added a narrow, tested pattern (`awaiting…critic`, catching "awaiting
   critic", "awaiting a fresh critic", "awaiting recriticism" — with an explicit negative case for
   "awaiting a critical fix", where `critic` is only the first six letters of an unrelated word).
4. **`reports/blog-feed.jsonl` is not a real collision.** `.gitattributes` already tells git to keep
   both sides' lines on this path (`merge=union`). Excluded exact-path matches on
   union-merge-declared paths from the conflict computation — directory claims are untouched, only
   the specific paths `.gitattributes` names.
5. **Freshness is now visible without opening five status files.** Every live piece in the default
   report and `--for <path>` output now shows age (git-log date of the status file, **not mtime** —
   see below) and a `[STALE? verify before trusting]` hint past 2 days.

**mtime was tried first and is wrong on this tree.** Hundreds of status files share the exact same
millisecond mtime (`2026-08-14T08:15:24.4xxZ`; 452 files fall into five such clusters) because a
checkout/bank pass touches the whole tree without changing file content. Switched to `git log -1
--format=%ct`, run only for live pieces (bounded by the live count, ~50-200, not the full 452).

**Self-test: 9 arms, `node tools/ownership.mjs --self-test`, all passing**, including both
directions of every fix above (a real collision still goes red; a declared-redundant one still
stays quiet; `status`-only files read correctly; `complete`/`incomplete` don't cross-contaminate;
`built_awaiting_critic` clears, "awaiting a critical fix" does not; an explicit
`ownership_claim_released` always wins).

Two of these (the last pair) were found by a general technique worth reusing: for every live
piece whose own `next_step` names a specific verdict file it intends to write, check whether that
exact file already exists and post-dates the status file. It is cheap, decisive, and exactly the
cross-check the dispatch asked for.

## What was checked and NOT cleared, and why — the more interesting half

**Candidates specifically investigated and kept live, with the reasoning:**

- **`PLAYABILITY`** (6.2 days old, flagged STALE by the tool). Its `next_step` opens with the word
  "SUPERSEDED" — which a shallow prefix-matching heuristic (used only for triage, never to clear
  anything automatically) flagged as a possible clear. Read in full: the sentence continues
  *"— see successor_run_3_FINAL_live_results… **What remains: (1)… (2)… (3)… (4)… (5)**…"* — five
  concrete, specific unfinished items. This is exactly the failure mode a shallow text match would
  have produced, and it is why nothing in this sweep was cleared on regex alone.
- **`W1-19-builder-codex-20260810`, `-continuation-20260810`, `-codex-final-20260811`,
  `-codex-persistent-20260811`** vs. the current front, `W1-19-builder-production-continuation-
  20260813`. Five successive builder rounds on the same piece, which looks at a glance like exactly
  the "old rounds never got retired" problem. Checked the newest round's own `redundant_with`
  field: it names only `W1-19-builder-production-20260811` (already correctly reported as
