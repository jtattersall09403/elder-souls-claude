## The root cause that matters more than the 32 rows: git-log date, not mtime

**The dispatch's own "17 recent, 14 old" split was computed from filesystem mtime, and mtime is
already a known-bad signal on this tree** — `OWNERSHIP-SWEEP-20260814.md` documented this for its
own purposes ("hundreds of files share the exact same millisecond mtime... because a
checkout/bank pass touches the whole tree without changing file content") and fixed it there by
switching to `git log -1 --format=%ct`. **This triage re-discovered the same bug independently,
in a different tool, causing a different kind of damage**: it does not create false conflicts, it
misfiles *how old a piece actually is*, which is exactly the number this dispatch's whole
prioritisation scheme (17 recent vs. 14 dead) rests on.

Measured directly, `orchestration/status/<f>.json` mtime-derived age vs. `git log -1 --format=%aI
-- orchestration/status/<f>.json`-derived age, for every piece this dispatch was told mattered:

| piece | mtime said | git-log says | error |
|---|---:|---:|---:|
| `W1-18` | 11.5 h | **122.1 h (5.1 days)** | **10.6×** |
| `W1-19-builder-codex-persistent-20260811` | 11.5 h | **75.6 h (3.2 days)** | **6.6×** |
| `W1-30-builder-20260812` | 11.5 h | 33.4 h | 2.9× |
| `W1-19-builder-production-continuation-20260813` | 11.5 h | 25.2 h | 2.2× |
| `W1-19-builder-production-20260811` | 11.5 h | 22.7 h | 2.0× |
| `W1-30` | 9.2 h | 9.7 h | ~1× (small) |
| all 14 pre-gap pieces | 150.8–196.4 h | 150.8–195.6 h | ~1× (mtime happened to agree here) |

**`W1-18` is the load-bearing example.** It was never in the dispatch's own named list of twelve
consequential recent pieces, but a naive mtime-based scan (the kind an orchestrator running this
same check quickly would reach for) puts it inside the valuable 11.5h band, one slot away from
`W1-19-builder-*`. Its real content is the *original, pre-build wave-1 dispatch note* —
`outputs_written: []`, `next_step: "write game/src/sim/quest/* modules"` — five days stale, from
before `W1-18-r2`, `W1-18-builder-codex-20260810`, and *today's own three-commit re-integration*
all happened on top of it. Trusting mtime here would have spent a fresh dispatch re-reading a
brief the branch has already answered four times over.

**Fix, and it costs one line anywhere staleness is computed.** Any tool that answers "how old is
this piece" — `tools/dispatchable.mjs`, `tools/ownership.mjs`, a human doing this exact triage by
hand — should read `git log -1 --format=%ct -- <path>`, never `fs.statSync(path).mtimeMs`.
`tools/stranded-check.mjs` (built this dispatch, below) does this by construction.

## A second, independent root cause: real work lands under someone else's headline

This is the pattern behind three of the four `DONE`/near-DONE findings below, found three
separate times today by two separate dispatches:

1. `critic-w1-20` and `critic-w1-attr-scale` — found and fixed by `OWNERSHIP-SWEEP-20260814`
   earlier today. Both critics' verdicts landed at `1c4c487d`; neither status file was ever
   updated to say so.
2. `W1-20-r3-remediation` — found independently by this dispatch. All four numbered items in its
   brief are landed on `HEAD`, but not under a commit that names the piece: they arrived inside
   `1be74605`, an **orchestrator bank commit** titled *"HAZARDS 9: a -f flag only defeats
   gitignore..."* — a commit about an unrelated tooling fix, whose own generated message body
   (the ownership-registry accounting `bank.mjs` prints) is the only place this piece's name and
   files appear. See "Findings, in detail" below for the full evidence chain.

**The mechanism is structural, not a mistake any one agent made.** `bank.mjs`/`land.mjs` stage
and commit the whole shared working tree under one message so unbanked work does not die with a
container restart (rule 28's other half). That message *does* name every piece whose files it
carries — `bank.mjs` prints an ownership-registry accounting for exactly this reason — but nothing
reads that accounting back into the named pieces' own status files. The agent who would normally
write `"next_step": "done, verdict filed"` has usually already had its turn end by the time the
*orchestrator's* bank happens to sweep its uncommitted work into a commit; there is no one left to
write the update. Three confirmed instances in one day is enough to call this a class, not a
coincidence.

**What would close it mechanically** (not built this dispatch — flagged as the next lever):
`bank.mjs` already computes, for every commit it makes, which task IDs own which of the paths it
just carried. A cheap follow-up write — for each such task ID whose own status file still shows a
non-terminal state, append (not rewrite) a `bank_carried: {commit, date}` marker to that task's
status file in the same operation — would make this class self-documenting instead of requiring a
human/agent triage pass to notice it after the fact. `tools/stranded-check.mjs` (below) is the
detector; this would be the producer-side fix that makes the detector's job smaller over time.

## The mechanical check, built and proven to fire

`tools/stranded-check.mjs` — warning-only, changes nothing, exits 0 on a normal run. For every
non-terminal status file it: (1) computes the file's own true age via `git log`, never `mtime`;
(2) checks every path in `files_touched`/`files_claimed`/`outputs_written`/`outputs_expected` for
commits landed *after* the status file's own last commit — a positive hit means the piece (or a
file it claims) kept moving on the branch after its status file stopped saying so; (3) checks
whether `next_step` names a `corpus/90-verdicts/**` path that already exists on disk, the
technique `OWNERSHIP-SWEEP-20260814.md` used by hand to clear `critic-w1-20` and
`critic-w1-attr-scale`, now automated.

**`node tools/stranded-check.mjs --self-test` proves it fires**, on two arms:

1. `W1-20-r3-remediation` (this dispatch's own headline finding) — flagged with four
   `post-status-commit` hits including the exact `1be74605` bank commit identified by hand above.
   The self-test is written to fall through to a second fixture on any re-run *after* this
   dispatch's own triage corrects that piece's state (expected — it is no longer a candidate once
   fixed, which is success, not fixture rot).
2. `W1-DOOR-YAW-SWEEP` — deliberately left non-terminal by this triage (real work remains) but
   still shows genuine post-status drift (`reports/door-yaw/sweep-after.json` and three siblings
   written to disk *after* the status file's last commit — see that piece's finding below). Stays
   a valid fixture across repeated runs because this triage does not resolve it to terminal.
3. Negative arm: a synthetic `state: "done"` is confirmed **not** flagged, so the tool is not
   trivially positive on everything.

A high-recall, low-precision run against the live tree right now flags 30 of 33 non-terminal
pieces (one more exists now than at the top of this report because the tree moved during the
triage itself — expected on a fleet this size, not a bug). That is intentionally noisy: hub files
(`game/src/engine.js`, anything with ≥5 post-status commits) are explicitly annotated
`[hub file, many owners -- read the diff, do not trust the count alone]` rather than silently
trusted, and `reports/blog-feed.jsonl` (union-merged, every piece appends one line) is excluded
entirely as carrying no per-piece signal — the same exclusion `OWNERSHIP-SWEEP-20260814` made for
its own conflict computation, applied here to drift detection instead. **This is meant to be run
routinely as a cheap warning, the way `ownership.mjs --conflicts` already is** — wiring it into
`dispatchable.mjs`'s own report (so a dispatcher sees "N post-status commits" beside a piece's
`next_step` the moment they look it up) is the natural next step and was not done this dispatch;
the tool stands alone and is safe to run as-is.
