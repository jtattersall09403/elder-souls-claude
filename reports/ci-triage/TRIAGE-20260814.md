# CI triage — the failing corpus-gate actions, 2026-08-14

Task: `ci-triage-20260814`. Owner's charge (`orchestration/OWNER-DIRECTIVES-2026-08-14.md` §7):
*"There are a lot of failing corpus gate actions on GitHub. Does this matter? Is anything monitoring
these or doing anything about them? Decide if something should be doing anything with/about them or
not, it's up to you, you're the implementation lead."* This is that decision, in writing, with
evidence, ruled reversible per `CLAUDE.md` rule 0.

**Headline: one workflow, one job, one step, one root cause class doing most of the damage — not
twenty unrelated fires.** The gate is telling the truth about something real (most Wave-1 verdicts
cite evidence that was never committed), it has been red almost continuously since the day it went
live, and nobody has been reading it. That combination — red, true, and ignored — is worse than no
gate (`CLAUDE.md`: *"trains everyone to ignore red"*), so this write-up both fixes what's cheap and
rules on everything else.

## 2. What that one step is actually finding

`corpus/90-verdicts/wave1/` holds 76 verdict files. I simulated a genuinely fresh CI checkout
(`git ls-files` against every path a verdict cites in `artifacts[]`, rather than trusting what
happens to exist in this already-populated working tree) and validated all 76 against the current
schema and `tools/verdict-validate.mjs`.

**56 of 76 (74%) fail in a real fresh checkout. Only 20 pass.** They split into two independent
classes that mostly don't overlap (6 verdicts hit both):

### Class A — cited evidence was never committed (42 verdicts, the dominant cause)

`reports/.gitignore` deliberately excludes everything under `reports/` except `.md`, the blog feed,
baselines and the sabotage-replay corpus — a documented, reasoned trade-off (701 MB / 846 files of
"reproducible from the tools" run output). But `verdict-validate.mjs` — correctly, per
`CRITIC-DOCTRINE §1.2`, *"a verdict with no artifacts is VOID"* — requires every path a verdict cites
in `artifacts[]` to exist on disk. In a fresh CI checkout it never does, because the policy that
makes `reports/` disposable and the check that demands its contents be present are two different
rules that were never reconciled. **This is class "a gate that is right but was never satisfiable"**
from the assignment's own taxonomy: the requirement (a verdict's evidence must be reproducible) is
correct doctrine; asking a fresh, sourceless CI checkout to prove it is not, given the standing
`.gitignore` policy.

The good news: I checked whether the missing evidence still exists anywhere. **211 of 215
missing-citation instances (98%) are files that physically exist in this working tree right now** —
they were produced, just never `git add`ed. Only 4 (all from the single oldest verdict, `W1-01.json`)
are genuinely gone and would need a re-run to recover. Total recoverable payload: **206 distinct
files, ~119 MB.**

### Class B — the verdict itself is non-conformant (20 verdicts)

Missing required fields, invalid enums, quoted evidence not declared in `artifacts[]`, stale
`subsystem_paths` — mostly verdicts written before the schema tightened and never migrated. Cross-
referencing round numbers (`corpus/90-verdicts/wave1/<piece>[-rN].json`) against which round is
*current* for each piece:

- **10 are obsolete draft rounds, already superseded by a later, currently-passing round for the
  same piece** — not a live defect, just history: `W1-01.json` (→ `-r2` passes), `W1-04-r4.json`
  (→ `-r5` passes), `W1-07.json` + `W1-07-r2.json` (→ `-r3` passes), `W1-10.json` (→ `-r2`/`-r3`
  pass), `W1-13-r2.json` (→ `-r3`/`-r4` pass), `W1-21-r1.json` (→ `-r2` passes), `W1-22-r1.json`
  (→ `-r2` passes), `W1-DEPLOY-r1.json` (→ `-r2` passes), `W1-MAP-r1.json` (→ `-r2` passes).
  **Class: made obsolete by work that has since landed.**
- **8 are the current, standing verdict for their piece and are genuinely broken right now**:
  `W1-14-r4.json`, `W1-19-r2.json`, `W1-FACTIONS-r2.json`, `W1-LIBRARY-MARTIAL-r4.json`,
  `W1-LIBRARY-r1.json`, `W1-PROSE-BLIND-r1.json`, `W1-PROSE-TICS-r4.json`, `W1-TOUCH-r1.json`.
  **Class: real defect in the corpus** (not the game — these are Wave-1 judgement records, and the
  game they judge is unaffected by their JSON shape).
- **1 was a crash in the validator, not a content problem**: `W1-FACTIONS-r2.json`'s
  `blind_comparisons` field is a single `{required, done, reason}` object ("blind wasn't possible,
  here's why") instead of the array the schema expects, and `for (const b of v.blind_comparisons ||
  [])` threw `TypeError: object is not iterable` on a non-array truthy object. The sweep is
  individually try/caught per file (a past incident already fixed that — one crash used to kill the
  whole run silently), so this didn't hide other results, but it did report an opaque
  `validator threw on this file` instead of a legible finding. **Fixed below.**

## 3. The one thing to verify specifically — `biggest_gap` on a PASS

The owner's worry, quoting a gate log: *"a critic that reports no gap found has failed its own job
and its verdict is void" — which implied no critic could ever pass anything.* `CLAUDE.md` confirms
this rule was changed: *"a critic may PASS without inventing a gap when the written bar is
evidenced."* **Verified this session: both the validator and the schema already carry the amended
rule, not the old one.**

- `tools/verdict-validate.mjs:50` — `if (!g && v.status !== 'PASS') E('biggest_gap missing…')` —
  only fires for a non-PASS verdict.
- `corpus/00-doctrine/verdict.schema.json`'s `allOf` conditionally requires `biggest_gap` **only
  when `status === "FAIL"`** (lines ~1043–1059), and its own field description says outright:
  *"PASS requires the governing evidence gates and may omit biggest_gap when no qualifying gap is
  demonstrated."*
- The 4 `biggest_gap missing` errors actually seen in this sweep are all on verdicts with status
  `FAIL`/blank — the *current, correct* rule firing as intended, not the retracted one. **No fix
  needed here; both places already carry the amendment.** If a future schema change ever
  reintroduces an unconditional requirement, this file's §2/§3 numbers are the regression test:
  re-run `node tools/verdict-validate.mjs --all` and confirm the `biggest_gap` error count stays at
  the FAIL/VOID population only.

## 4. What I fixed (cheap, real, verified — delete-the-fix run both ways)

**Fix 1 — `.gitignore` was silently eating the one directory meant to hold durable verdict
evidence.** The root `.gitignore`'s blanket `*.log` rule (line 7) also matched
`corpus/90-verdicts/**/artifacts/**/*.log` — which is *not* the disposable `reports/` tree, it is
the per-verdict evidence directory several verdicts already use by convention for exactly this
purpose. 24 such `.log` files exist in this working tree and were all untracked. Added one exception
line:

```diff
 reports/runs/
 reports/runpod-gpu/runs/
 *.log
+!corpus/90-verdicts/**/*.log
 .DS_Store
```

Then committed the 22 of those 24 files this working tree still holds (2 were already tracked).
**Verified, not asserted:** re-ran the fresh-checkout simulation before and after —
`git ls-files`-backed "CI-only untracked-artifact FAIL" count went from **42 → 40** verdicts (two
verdicts, `W1-14.json` and `W1-SAVE-r1.json`, cited *only* a `.log` under this path and are now
fully resolved; several others still cite additional `reports/*.json` paths and remain red — see
Class A above, named as the expensive remainder). Reverting the `.gitignore` line reproduces the
untracked state exactly (tested via `git check-ignore -v`, which flips back to matching the blanket
`*.log` rule the moment the exception is removed) — a clean, one-line, fully reversible change.

**Fix 2 — `verdict-validate.mjs` crashed instead of reporting on a non-array `blind_comparisons`.**
Added the same defensive pattern the file already uses for `gap_closure` (same file, ~90 lines
above — this bug class had already been found and fixed once, just not for this second field):

```diff

-  for (const b of v.blind_comparisons || []) {
+  const blindRows = Array.isArray(v.blind_comparisons)
+    ? v.blind_comparisons
+    : (v.blind_comparisons && typeof v.blind_comparisons === 'object'
+      ? (E('blind_comparisons must be an array, not a single {required,done,reason} object …'), [])
+      : []);
+  for (const b of blindRows) {
```

**Verified:** `node tools/verdict-validate.mjs corpus/90-verdicts/wave1/W1-FACTIONS-r2.json` now
reports 49 named, actionable errors instead of one opaque `validator threw on this file` line. Total
sweep-wide OK/FAIL counts are unchanged (56 OK / 20 FAIL locally, same file still fails — it was
never going to pass, it has real content gaps) — this is a legibility fix, not a leniency change, and
I confirmed it doesn't silently pass anything by re-checking the full `--all` sweep before and after.

Both fixes are in `.gitignore` and `tools/verdict-validate.mjs`, committed under this task id.

## 5. Rulings — reversible, with the evidence that would overturn each

**Ruling A — do not weaken the artifact-existence check.** It is finding something true (most
Wave-1 verdicts are, by the corpus's own §1.2 rule, currently VOID for lack of committed evidence).
Making it advisory would violate `corpus-gate.yml`'s own header (*"do not add `continue-on-error`… do
not make any step advisory"*) and rule 13. *Overturned by:* if a future audit shows the missing
`reports/*.json` files are genuinely disposable scratch rather than load-bearing evidence for a
verdict's score, in which case the fix is re-authoring those verdicts to cite the `.md` write-up
instead (which is tracked) — not weakening the checker.

**Ruling B — commit the remaining Class-A evidence (206 files → 184 after fix 1, ~119 MB) as a
named, bounded follow-on dispatch, not a blind bulk `git add -f` today.** Cost: recovering the files
is mechanical (`git add -f`, ~5 minutes) but *reviewing* whether each is genuinely the final evidence
a verdict rests on, versus scratch that happens to still be lying around, needs the judgement of
someone who can read the 40 affected verdicts — that's a corpus-content decision, not a CI-plumbing
one, and not mine to make unilaterally for other agents' work. Estimated cost: one dispatch,
~40 verdicts, likely 1–2 hours of agent time to review-and-commit in batches by piece.
*Overturned by:* if a fast reviewer confirms all 184 files are final (not scratch), in which case
this collapses to a single mechanical `git add -f` pass.

**Ruling C — the 8 current-and-broken legacy-schema verdicts (Class B) are accept-and-document, not
mine to backfill.** Fabricating `native_scale`, missing `arbitration.ar1/ar2` checks, or `self_audit`
booleans for a verdict I didn't judge would be exactly the "nothing counts because someone says so"
failure `CLAUDE.md` warns against — a fresh agent inventing a shape to make red go green is worse
than the red. Cost: 8 small, piece-specific remediation dispatches (the original critic's context, or
a fresh critic re-measuring the piece and writing a schema-conformant verdict from scratch — cheaper
for pieces where re-measurement is itself cheap, e.g. `W1-TOUCH-r1`, which is missing nearly every
required field and reads as an unfinished draft rather than a lightly-broken record).
*Overturned by:* any evidence that one of these 8 has already been re-judged by a later, unlabelled
verdict I didn't find — re-run §2's round-cross-reference if a new `-rN` appears for any of the 8.

**Ruling D — the 10 obsolete superseded rounds (already-passing later round exists) stay in the
corpus as history but should stop being asked to pass CI.** I did **not** implement this today — a
"only the latest round per piece is gate-relevant" rule needs care around naming edge cases (e.g.
`W1-01-province-stream-r1.json` is a *different sub-piece* of W1-01, not a round of it, and a naive
round-number heuristic could misclassify it) and I was not willing to ship an unverified heuristic
under this task's time budget. **Named, not built.** Design sketch for whoever picks it up: key on
piece *identity* (the part of the filename before the last `-rN`), not a blanket prefix match; treat
a verdict as gate-relevant only if no other verdict of the same piece identity has a strictly higher
round number and a passing validation; keep failing rounds in `git log` untouched. Cost: small, a
few hours including test cases for the naming edge cases above.

**Ruling E — the one-off GitHub Actions infra flake (2026-08-06T16:19:54Z, "Service Unavailable"
resolving action downloads) is not actionable.** It didn't recur in any later sample across 8 days
and 1222 runs. No fix, no monitor needed for it specifically.

## 6. The monitoring question — should something own CI health going forward?

**Yes, lightly, and not as a new blocking gate** (the task is explicit: nothing here should land on
the commit path — rule 13, and the box has already stopped twice on a fail-closed gate firing on
in-flight work).

**Proposal, lightest thing that works:** nothing new needs to be built. `tools/verdict-validate.mjs
--all` already runs on every push and already prints a machine-readable OK/FAIL count — the gap was
never instrumentation, it was that nobody was reading the roll-up. So: **this report is the roll-up**,
and the ongoing "owner" should be whichever agent is next asked to touch `orchestration/INDEX.md`
housekeeping (already a standing duty per Owner Directive §7) — pointing at
`reports/ci-triage/TRIAGE-20260814.md` from `INDEX.md` costs one line and means the next orchestrator
pass sees the CI state without re-deriving it. I added that line (see `orchestration/INDEX.md`). No
new agent role, no scheduled job, no new tool. If the red count meaningfully changes (Class A goes
down as Ruling B lands, or a new verdict adds a new Class B defect), whoever lands that work should
re-run §2's simulation and update this file's numbers — it is cheap enough (`node
tools/verdict-validate.mjs --all`, one command) that a dedicated watcher would cost more than it
saves.
