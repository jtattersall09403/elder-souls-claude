## 2. Job two — five things the instrument could not see, and now can

### 2a. The blocker: the suite was destroying its own results

The predecessor's `M-K8` reloads the page for a cold-profile pointer-lock measurement, then did:

```js
await page.waitForFunction(() => !!(window.__HARNESS && window.__HARNESS.getInputState));
await page.evaluate(() => window.__HARNESS.ready()).catch(() => {});
```

Both lines are wrong in the same direction. `window.__HARNESS` is installed with its full method
table **before** `Engine.boot()` resolves, so the first returns while the engine is still
building. The second is the real damage: `page.evaluate` has a **30 s default timeout**, the boot
exceeds it routinely at load 20+, `ready()` rejected — and `.catch(() => {})` **ate the
rejection**.

What that produced, in order:

1. `M-K8` and `M-K9` **flapped between pass and FAIL on identical builds**. `getInputState()`
   falls back to a `real`-less stub reporting `pointerLocked: false`, so M-K9 counted ten frames
   of "gameplay with no lock and no menu" and raised **HF4 against a build that never violated
   it**.
2. `padChecks` then threw `gamepad(): no real input path on this engine`, which reached
   `main()`'s single `try`, which called `die()` — and **`die()` runs before `writeJson`**. A run
   that had already measured twenty checks wrote **no file at all**.

Fixed three ways: `reattachAfterReload()` waits on `__ENGINE.real` being present *and attached*
with a 240 s budget and **throws rather than swallows**; each group now runs inside its own
survival wrapper that records a throw as a `GROUP/<name>` unmeasurable entry and continues; and
the page is re-proved live between groups, because `desktop` reloads it.

**A group that did not run and a group that ran and found nothing are no longer the same output.**

### 2b. M-K22 was raising a hard fail against the prose team, from a bug in the grader

The check carried this comment —

> *Key names as WORDS (a prop called "Reed" must not trip on the letter R)*

— directly above `CONTROL_WORDS.filter((w) => low.includes(w))`, a plain substring test. The
comment stated the rule; the code did not implement it. It reported **sixteen violations**, every
one of them an ordinary Argonian name:

| String | "violation" |
|---|---|
| Waits-For-Salt the Sho**rt**er | `rt` |
| Silent-Reed Bone-Setter of sti**lt** town | `lt` |
| Ocheeva S**alt**-Hand | `alt`, `lt` |

That is the mirror image of M-K20's round-1 defect and just as dishonest: a check that fires on
nothing real trains its reader to ignore it. The two token classes cannot share a matcher, so
they no longer do — the two-letter pad glyphs (`rt`, `lt`, `rb`, `r1`…) are anchored on **both**
sides; the phrases (`press`, `left click`, `d-pad`) are anchored left and may inflect right, so
"presses" and "buttons" are still caught. `-` is a word boundary, which is what makes "Salt-Hand"
safe and "L-Trigger" still a hit.

And the matcher now carries **its own control**, computed and published in the detail: three
strings that must hit ("Press E to pull", "Hold RT to charge", "Left click to swing") and three
that must not ("Waits-For-Salt the Shorter of rot quarter", …). **If the control fails, M-K22
reports `unmeasurable` rather than grading with a broken lexicon.**

### 2c. M-K21 found a real hole in the build — and its own DS3 leg was vacuous too

The census swept eight named states and found **zero readable entities**. That matters more than
four points: `DS1` sets the tutorial budget at **zero for the whole game**, and `DS2` names the
only sanctioned thing allowed instead — an inscription, *"a physical entity with a position,
readable via `interact`, written in-fiction by someone who was there"*. **The build had taken the
prohibition and shipped none of the remedy**: a game that may not tell you anything and did not
show you anything either.

All three of M-K21's thresholds are **upper bounds** (≤ 6, ≤ 14, 100 % within 8 m), so an empty
world satisfies every one of them — the last one vacuously. That is a grep over an empty set with
a different noun, and the check refuses it explicitly.

Built: `game/data/world/inscriptions.json` — **10 inscriptions across 5 states, 4 of them before
the first meaningful choice**, every DS4 verb (`interact`, `light`, `roll`, `block`, `sprint`)
covered, none of them addressing the player and none naming a control:

> *"Sixty-one days. The hasp turns if you have the hands for it. I did not, at first."*
> *"The dray came down this street at a gallop and I went sideways into the gutter and lived.
> Halim stood still and reasoned about it. Halim is under the chapel."*

Kept in **one file** rather than sprinkled into the state files, for two reasons: three of those
states are owned by W1-07 and this is not W1-07's work, and DS2's budget is a property of the
*journey* — "≤ 6 before the first meaningful choice" cannot be enforced by six files that each
hold one and cannot see the others. `Engine._spawnInscriptions()` **throws on boot** if the file
goes over budget.

**And the check's own DS3 leg was vacuous.** It read
`f.distance_to_first_use_m === undefined || <= 8`, and **nothing ever set that field**, so the 8 m
threshold could not be failed by any build. It now measures from the inscription to the position
its record names for the situation, and an inscription naming **no** situation is a **miss**, not
a pass. Measured: 0.57 m – 2.06 m.

**Confirmed the code I changed actually runs**, and delete-the-fix on it: nulling
`engine.data.inscriptions` returns the census to **0**; restoring returns it to **2** in
`barge-hold`.

## 3. Seam S35 — reconciled, and it changed something

S30 is overruled; there is a map. **Nothing of mine assumed there was not one**, and that is worth
stating precisely rather than waving at:

* The action set is **closed at sixteen** (`RI-JRN03` §B), so no `map` action was ever needed and
  adding one would break M-K1's 16/16.
* The map is a **menu screen**. `menu` is `Escape`/`KeyM` on desktop, present on both pad profiles,
  and lives in the **touch drawer** — so a touch-only player reaches it. Reachability was already
  correct.

**What did need reconciling:** `ui/system.js` draws the touch overlay *after* the screens and
outside `beginScreen()`, deliberately — opening the inventory on a phone should dim the inventory,
not the controls you close it with. That is right for the inventory and **wrong for a screen you
are meant to read**. Eleven combat marks across a chart of the coast is the same offence as a
marker on it, arrived at from the other side, and on an 844×390 phone the ring covers a quarter
of the map.

It is also a **discoverability** defect independent of S35, and that is what makes it an input
ruling rather than a taste one: `UISystem.step()` consumes the action set while a full-screen
surface is open, so a blade drawn over an open book is **a control that cannot do anything if
pressed**. §F's whole mechanism is that what the player can see, they can try.

So the ring is suppressed on `map`, `journal` and `book` only — **and the drawer stays**, because
suppressing the controls that do nothing must never suppress the one that does. `inventory` is
deliberately not on the list: you *act* in the inventory, so its controls are live.

**My own first draft of this rule was wrong, and probing it is what caught it.** It set
`shown: false` outright — which took `controls_drawn` to 0 on the map, **which took the drawer
with it**, and `menu` lives in the drawer. The touch profile declares no gestures, so there was
no other affordance on the glass: a touch-only player who opened the map **could not close it.**
A control legend is a defect; a trapped player is a worse one.

The second draft had a subtler version of the same fault. Filtering the controls in the overlay
*model* would have left them invisible and **still pressable**, because `TouchInput.layout()`
feeds the **hit test** as well as the drawing. The property the whole overlay rests on is that
what is drawn is what is pressable, in both directions — so the suppression is a field on the
input model (`TouchInput.suppressToDrawer`), set every frame from `UISystem.mode`, and both
readers see the same list.

Measured, on an 844×390 handheld viewport:

| Surface | drawn | hit-testable | actions |
|---|---:|---:|---|
| world | 11 | 11 | the full arc + drawer |
| **map** | **1** | **1** | `__drawer` |
| **journal** | **1** | **1** | `__drawer` |
| inventory | 11 | 11 | full arc — correctly not suppressed |
| world, after | 11 | 11 | restored with nothing having to remember to |
| **map, drawer open** | **6** | **6** | `__drawer, two_hand, swap_left, swap_right, spell_cycle, **menu**` |

Drawn equals hit-testable in every row, and **`menu` is reachable on the map**. Delete-the-fix on
the first draft (`_touchScreenSuppression` forced to `null`) put 11 combat marks back across the
chart. The model reports `suppressed_by_screen: 'map'` rather than merely going quiet, so a
critic reading a low `controls_drawn` on a phone can tell an S35 suppression from the round-1
defect coming back. `M-P21`'s sixteen-action reachability is measured in the world and is
untouched.

I did **not** build the map; a separate builder owns it.

## 3b. The full `--self-test` had never been run to the end, and it was hiding a real defect

Everything above was written before the suite had ever completed a `--self-test` pass. It has now
run four times end to end, and the first complete run **exited 1** with seven vacuous legs and
three red checks. What that pass found is the point of this section, because none of it was
visible from any partial run.

### 3b.1 The reattach that was written to stop half-booted runs threw on every call

`reattachAfterReload()` — round 2's own headline instrument fix, with a forty-line comment
explaining the failure it prevents — ended its first real statement with:

```js
await page.evaluate(async () => { … }, undefined, { timeout: 240000 });
```

**`page.evaluate` takes `(pageFunction, arg)` and nothing else.** Playwright answers a third
argument with `Too many arguments. If you need to pass more than 1 argument to the function wrap
them in an object.` So the function threw at every group boundary in every run, `__HARNESS.ready()`
was never awaited, and the page helpers were never reinstalled. The suite then wrote **five**
`PAGE/after-<group>` entries reading *"the page could not be returned to a measurable state"*,
carrying the threshold text *"every later group in this run is unmeasurable"* — **beside forty
later checks reporting `pass` in the same file.** A false `unmeasurable` is the mirror image of
round 1's false `pass`, and it was inside the function written to stop exactly that.

The budget is real now and belongs to `waitForFunction`, the only API here that has one: `ready()`
is started once page-side and its settlement parked on a flag that is then polled. And the group
boundary **re-samples the page after the attempt** instead of predicting the future — a claim
about later groups is now made from an observation of the page, or not made.

*Delete-the-fix:* re-introducing the third argument brings the false entries straight back —
`desktop,rebind` goes from **25/25 pass, 0 unmeasurable** to **24/27 with 3 unmeasurable**.

### 3b.2 Two rebind checks had been red for a round, and the rebinding surface was fine

`M-K18` (HF9) and `M-P23` reported `began: false` on **every** modality, `steps:
["idle","idle","idle"]`. Bisected against the same build: `--group rebind` alone passed 4/4;
`--group viewport,rebind` failed. Five separate causes, none of them in the rebinding surface:

| What the check inherited | What it did to the measurement |
|---|---|
| `M-P20` ends on `openMenu('book')` | a screen takes `interact` every frame (S14) — all three modalities dead |
| `M-P20` also **enters the census** | the census has a typed field, so it holds the **keyboard only** — which is why a dead keyboard leg sat beside a live pad one and read like a defect in the keyboard path. `reset()` does not stand an entered census down; `censusBegin({})` does, by re-arming it paused |
| the viewport group leaves `pointer: coarse` | `GamepadRouter` selects `souls-handheld`, where index 0 is `jump`, not `interact` — the check was pressing A and calling the surface uncompletable |
| the pad group ends on `H.gamepad(null)` | the pad was unplugged; a freshly arrived pad correctly produces no presses from its arrival state |
| `M-P15` ends having **calibrated a stranger** | see 3b.3 — the profile's `interact` index fired `roll` |

The check now **asserts and records its preconditions** rather than inheriting them — ui mode,
device class, pad profile, census — drives whatever control the *active* profile gives `interact`
(honouring the handheld tap/hold gate), runs the pad leg on **both** shipped profiles rather than
one, reads the surface over a short window instead of one nominated frame, and **proves the pad's
`interact` index actually fires `interact` before it measures anything**. If it cannot establish
that, it reports `unmeasurable` **naming the action the pad really fired** — because "the surface
is not completable on a pad" and "I never managed to send it the press" are different claims.

### 3b.3 The defect the repaired instrument then found: a calibration that outlived its pad

With the check made to prove its own precondition, it stopped failing silently and said what was
wrong: *the profile's own interact index did not produce interact — souls-default fired
`["roll"]`.*

`M-P15` calibrates an unrecognised pad ("Some Unknown Pad 9000"), which is its job. `_adoptPad`
already refuses to hand a newly arrived pad the previous one's profile and quirk map — its comment
says so in as many words — but `calibrationResult` is **instance** state, set when a calibration
completes and only ever replaced when a *remembered* id comes back. So the permutation a player
taught an unrecognised pad went on being applied to **every pad plugged in afterwards**.

Measured, on the shipped build, with no instrument in the loop:

| Step | before | after the one-line fix |
|---|---|---|
| calibrate the stranger (6 inputs), press its raw 0 | `light` | `light` |
| unplug it, plug in a **standard** pad, press index 0 | **`roll`** | **`interact`** |
| …press index 5 | **`lock_on`** | **`light`** |
| plug the stranger back in, press raw 0 (L5 memory) | `light` | `light` |

The fix is that a learned permutation applies only to the pad id it was learned on
(`game/src/input/gamepad.js`). **Delete-the-fix reproduces `roll` and `lock_on` exactly.** In a
player's hands this is: calibrate an odd pad once, swap to a normal one, and A rolls instead of
opening the door — with L5's "a pad you have used before keeps its calibration" still intact,
which is why the fix is a match on the id and not a clearing of the memory.
