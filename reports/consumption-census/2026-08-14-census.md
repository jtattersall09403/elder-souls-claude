## What this is, and what it is not

A **name-grep census** over every `game/data/**/*.json` field family, plus a manual, source-to-sink
trace on the fields ranked most likely to be visible to a player. It is the mechanical first pass
`RI-MTH07` itself describes — *"a grep for the field name is where you start, not where you
stop"* — and I stopped at different depths for different fields depending on likely impact, which
is exactly the tension the dispatch brief names. Read the confidence column, not just the class.

**What I could not do, stated first:**

- **No live browser perturb-and-observe was run for the top 10.** `node tools/contention.mjs
  --gate` reported the box at 8 browser instances against a ceiling of 6 at the time I would have
  needed one (RULES.md rule 21: wait or do non-browser work). I did non-browser work instead: for
  the highest-ranked candidates I read the actual consuming function line-by-line and confirmed
  either (a) the field is never referenced by name anywhere reachable, or (b) the *equivalent*
  behaviour is separately hard-coded, bypassing the authored field entirely. That is stronger than
  a name grep — it establishes *what the code does instead*, not just that a string doesn't
  appear — but it is not the same as watching an entity change on screen. Anywhere below marked
  `STATIC-TRACE` should still get a browser confirmation before anyone spends effort fixing it.
- **648 name-grep orphan candidates were not individually traced.** At this project's scale (2,482
  scanned field names across 588 data files) that would be a multi-day effort on its own. I did
  trace the ~40 fields listed under "Verified findings" below, chose them by scanning for the
  fields most likely to be player-visible (combat feel, quest state, world content), and I
  flagged entire buckets (`camera`, most of `stealth`, most of `crime`) as **UNRESOLVED-AGGREGATE**
  rather than orphan, because a sample check showed those directories mix real gameplay data with
  embedded calibration/acceptance-criteria documents that are legitimately read only by critic
  tooling, not the running game — see "The false-orphan pattern" below. Counting those as orphan
  would be exactly the wrong-CONSUMED-shaped mistake in the other direction: confidently wrong,
  in bulk.
- **The four defects named in the dispatch brief** (`userData.surfaceUniforms`, `sim.env.region`,
  dialogue `name`, fog-altitude thinning) were re-checked against the current tree, not
  re-discovered. Status for each is below. I did not attempt to fix any of them.

## Method

1. `game/data/**/*.json` walked and grouped by directory family (33 groups — sibling files in one
   family share a schema, e.g. `combat/movesets` vs `combat/enemies`).
2. Field names collected per group (id-keyed rosters like the 87-weapon moveset set or the
   1,160-clip registry are sampled once, not exploded into thousands of ID strings).
3. Commentary/provenance fields (`*_note`, `*_rationale`, `why_*`, `corpus_item`, …) filtered —
   they are prose about the record, not data the game reads, and counting them as orphans would
   manufacture false findings out of this corpus's own annotation style.
4. Each remaining field name checked by word-boundary match against every `.js` file under
   `game/src/` (CONSUMED), then `tools/` (TOOLING-ONLY — a critic/build-time reader only, which
   `RI-MTH07 §B.1` explicitly excludes: *"a field that only a critic ever reads is instrumentation,
   not gameplay"*), else ORPHAN CANDIDATE.
5. Manual trace on the highest-likely-impact candidates: read the actual consumer (or confirm
   there is none), and for runtime-written fields (`userData.*`, `sim.*`), enumerate every write
   site and ask whether any of them run per-tick/per-position rather than only at boot or
   save-load — the mechanical check that catches `WRITTEN-NEVER-UPDATED`, which a name grep cannot
   (the field IS read, so it never shows up as a grep miss).

### The false-orphan pattern this census found and did not chase further

`game/data/camera/reference-framing.json` and several files under `stealth/` and `crime/` are
**embedded acceptance/calibration documents** — fields like `p95_darm_max`, `fft_peak_ratio_max`,
`worst_case_arm_under_soft_driver_m` are bars a critic checks a capture against, not values the
running camera reads. `reference-framing.json` is even fetched at boot (`game/data/index.json`
lists it) — its bytes are downloaded and counted in the boot payload, but its individual
conclusions are cited only in a source comment in `game/src/sim/camera.js:725`, transcribed by
hand into hard-coded constants. That is a real and interesting borderline case (fetched but not
parsed; values duplicated by hand rather than read) but it is not the same shape as `surfaceUniforms`
or `sim.env.region`, and mass-labelling `camera`/`stealth`/`crime`'s 100+96+105 candidates without
checking which are this pattern versus real unread gameplay fields would be guessing at scale. I
flag the three directories as **UNRESOLVED-AGGREGATE** and recommend a follow-up pass scoped to
just those three, now that this pattern is named.

## Verified findings — ranked by likely visible impact

This is the list `RI-MTH07 §B` and the dispatch brief ask for: real trace, not just a grep miss.
Confidence: **STATIC-TRACE** = read the exact consumer function and confirmed the field plays no
role, or found the parallel hard-coded logic that stands in for it. **GREP-ONLY** = zero hits, not
further traced. All are currently **unowned** as far as `node tools/ownership.mjs --for` could show
(re-check before dispatching — this census does not itself claim ownership of any file).

### 1. Combat moveset `slots.*.trigger` (button / modifier / state_window) — ORPHANED, STATIC-TRACE, highest impact

**87 weapon moveset files** (`game/data/combat/movesets/*.json`), every slot, every one of them,
carries a `trigger: {button, modifier, state_window}` object describing which input and which
player state should reach that slot. `game/src/combat/moveset.js`'s `resolveSlot(weaponId, button,
ctx)` — the function that actually decides which slot a button press resolves to — **never reads
`.trigger` at all** (confirmed: zero references to `trigger` as a property access in
`moveset.js`/`moves.js`/`player.js`). Instead the gating logic is hand-written as a long chain of
`if (ctx.state === 'IDLE' ...)`, `if (button === 'light') ...` checks (`moveset.js:524-675`), which
happens to implement the same rules the `trigger` objects describe, by hand, a second time.

This is `RULES.md` rule 10's "two parallel implementations of one system": today they agree, but
`trigger.button`/`trigger.state_window` are authored on thousands of slot records across every
weapon in the game and **editing any of them changes nothing** — the hard-coded chain in
`resolveSlot` is the sole authority. A future weapon-balance edit made against the data (which is
where an editor would naturally look) would silently do nothing.

- **Consumer named:** none. `resolveSlot()` is the only plausible reader and does not read it.
- **Confidence:** STATIC-TRACE (full read of `moveset.js:519-675`).
- **Not independently browser-verified.**

### 2. Combat moveset `cancels_into` — ORPHANED, STATIC-TRACE, high impact (roll-canceling)

Every slot in every one of the 87 weapon files carries `"cancels_into": ["dodge"]` (or similar).
This looks like the authored source for Souls-style roll-canceling out of an attack's recovery.
It is **not** what drives that mechanic: `game/src/combat/moves.js` computes a field called
`dodge_cancel_from` **by formula** — `startup + active_f + Math.ceil(0.45 * recovery_f) + 1`
(`moves.js:194,240,352,389`) — independent of the `cancels_into` array, and `player.js:287` gates
the actual roll-cancel input off `dodge_cancel_from`, never off `cancels_into`. `cancels_into` sits
on every slot, always says the same thing, and is never read.

- **Consumer named:** none for `cancels_into`. The real mechanic (`dodge_cancel_from`) has a real
  consumer at `player.js:287` — but it is computed independently, not derived from this field.
- **Confidence:** STATIC-TRACE.

### 3. Combat moveset `guardbreak_kind` — ORPHANED, STATIC-TRACE, medium-high impact

Authored per weapon (`"shoulder"`, `"thrust_through"`, `"kick"`, `"shield_bash"` — generated by
`tools/weapons/build-movesets.mjs:918` from a per-class grammar table) to presumably select a
different guardbreak animation/type per weapon class. The runtime resolves guardbreaks by a fixed
literal slot lookup — `pick('guardbreak', 'guardbreak')` at `moveset.js:564,627,668` — the *kind*
is never read anywhere. If the intent was "greatswords shoulder-check, halberds kick," nothing
currently makes that true; every weapon's guardbreak resolves the same slot ID regardless of its
declared kind.

- **Confidence:** STATIC-TRACE (grep confirmed zero references to `guardbreak_kind`; the
  `resolveSlot` guardbreak branches read only the literal slot name).

### 4. Combat moveset stance `exclusive_slots` — ORPHANED for gameplay (TOOLING-ONLY), medium impact

Declares which slots become unavailable in two-handed stance (e.g. `["2h.r2.follow",
"2h.roll.r2"]`). Read only by `tools/harness/critic-w1-10-static.mjs` and `tools/weapons/measure.mjs`
— both count/report on it for a verdict, neither is the running game. Per `RI-MTH07 §B.1` verbatim
("a field that only a critic ever reads is instrumentation, not gameplay") this is an orphan by the
item's own test, even though it has a reader. Practical effect: if a weapon is supposed to lock out
a specific follow-up while two-handed, nothing in `game/src` currently enforces it.

- **Confidence:** STATIC-TRACE (both readers checked directly; both are `tools/`, not `game/src/`).

### 5. Combat moveset stance `stamina_mult`/`motion_value_mult`/`poise_damage_mult` — ORPHANED but low severity

Same non-`game/src` reader pattern as #4. **Lower severity than it looks**, because
`tools/weapons/build-movesets.mjs:910-915` is the *generator* that writes these fields, and it
already bakes the multiplied values directly into each stance-specific slot's own
`motion_value`/`poise_damage`/`stamina` numbers at build time. The runtime reads the baked
per-slot numbers (which are correct) and never needs to re-apply the multiplier — so this triple is
closer to build-time provenance of a number already realised elsewhere than to a live defect. Still
technically ORPHANED per the census definition; flagged low-priority.

### 6. Combat enemy `reactable` — ORPHANED, GREP-ONLY, needs a browser check

Declared per enemy attack (e.g. `probe_pulse.json`'s `pulse.reactable: true`) and its own note cites
`RI-CMB12 §A`'s requirement that a `reactable_share >= 0.70` be *measured* — `t_react = f_active -
f_vis >= 19 f@60` — by `tools/harness/cmb-exchange.mjs --probe react`. Zero references to
`.reactable` anywhere in `game/src`. If nothing reads it, the measured reactable-share commitment
has nothing enforcing it at runtime (a boss could ship attacks that read as instant regardless of
what the data declares). Not independently re-verified whether `cmb-exchange.mjs` itself reads it
(that would make it TOOLING-ONLY, same class as #4) — **UNRESOLVED** on which of ORPHANED /
TOOLING-ONLY this is; either way, `game/src` does not consume it.

### 7. `game/data/world/settlements/*.json` — `targets` and `counts` blocks — ORPHANED, STATIC-TRACE

Every settlement file declares a `targets` block (how many named NPCs, taverns, guild halls,
quest-givers, etc. the settlement *should* have) and a parallel `counts` block (presumably a
self-audit of what was actually built). Neither is referenced anywhere in `game/src` **or**
`tools/` (checked directly — no hits for `.targets.named_npcs`, `.counts.named_interiors`, or
similar). This is authored content-completeness data with no automated check anywhere — the kind
of gap the project's own `RI-PRG06`-style census tools exist to prevent elsewhere, but this
specific pair of blocks has none. Lower direct player impact (it doesn't drive behaviour), higher
process impact: any status claim like "Lilmoth has its 30 named NPCs" is currently unverifiable by
tooling and would need a fresh census against the actual placed content, not against this field.

### 8. `game/data/items/*.json` — `droppable`, `granted_by`, `hand_placed`, `placed_at` — ORPHANED, STATIC-TRACE, low current severity

Zero references anywhere in `game/src`. Notably, **there is no item-drop function in `game/src` at
all** (searched for `dropItem`/a generic drop path; none exists) — so `droppable: false` on the
starting quest writ is not being *bypassed*, the capability it would gate does not exist yet. Real
orphan by the census definition, but forward-declared for an unbuilt feature rather than a live
bug. Re-flag this one specifically when item-dropping is implemented — that is the moment
`droppable` needs to become a real read, or a quest item becomes droppable-and-losable on day one.

## WRITTEN-NEVER-UPDATED

### `sim.env.region` — confirmed still red (already known; not this census's find, re-verified)

Exactly one write site in the entire tree: `game/src/save/state.js:828`
(`sim.env.region = blob.pose.region`), fired only on save-load. Contrast with siblings in the same
`sim.env` object, checked directly:

| Field | Write sites | Pattern |
|---|---|---|
| `sim.env.region` | `save/state.js` only | **stale** — never re-derived from player position |
| `sim.env.settlement` | `sim/settlement.js` (×2, on enter/exit), `engine.js`, `save/state.js` | live-updated as the player moves |
| `sim.env.interior` | `sim/settlement.js` (×3), `engine.js` (×2), `save/state.js` | live-updated |
| `sim.env.weather` | `engine.js` (×2, weather system), `save/state.js` | live-updated |
| `sim.env.tidePhase` | `engine.js` (tide system) | live-updated |

`sim.env.region` is read widely — `render/sky.js` (region-driven lighting/sky), `engine.js`
(resident-region tracking, journal region tags, arena checks), `sim/record.js`, `save/state.js` —
which is exactly what makes it dangerous per the method's own framing: it looks consumed from both
ends and is silently stale. `tools/metrics/consumption-census.mjs` now carries this as a standing
structural check (`WNU_CHECKS`) so a future fix — making it re-derive from position — is exactly
the thing that flips the tripwire from red to green, and a regression that reverts the fix goes red
again automatically. **Per the dispatch brief this is actively owned elsewhere; not touched here.**
